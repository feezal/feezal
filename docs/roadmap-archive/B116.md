# B116 — Gap-snap helper lines: show only the line being snapped to, not all four ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (08/2026).** Follow-up on [B113](B113.md) ✅: when a gap snap activates, four helper lines appear. Wanted exactly one — the line at the border of the dragged element where the snap will land. The gap arrows already tell the between-which-edges story; the extra lines only add noise.

## Which of the four survives

B113 drew a line at every end of both spans, which is the complete story and three lines too many. What earns its place is the **dragged element's own border** — where the snap will actually put it — and *how many* of those there are depends on the kind of proposal:

- a **rhythm** echoes one gap, so exactly one border closes it. Placing **after** the anchor that is the box's **leading** edge (`proposed.to`); placing **before** it, the **trailing** edge (`proposed.from`). The other border touches nothing.
- **centring** has a gap on each side, so **both** borders are snapped-to and both get a line: the leading edge closes the measured gap (`measured.to`), the trailing edge opens the proposed one (`proposed.from`).

Either way every line is an end of a span, so the arrows still terminate ON one at a right angle: B113's reading survives at a fraction of the ink.

**The centring half was a follow-up correction (08/2026, reported the same day).** The first cut treated centring like "placing before" and drew a single line, which shows half of what the snap is doing — the whole point of centring is the pair of equal gaps, and the element sits between them.

Per **axis**, so a position where both rhythms apply ([B112](B112.md) ✅) shows one vertical and one horizontal — and the [U99](U99.md) ✅ position readout rides along on whichever lines remain, now naming the positions the element is about to take.

The marker pools follow: `GAP_LINE_COUNT` went from four per axis to two (a rhythm uses one, centring both), derived in [feezal-canvas-gaps.js](../../www/src/feezal-canvas-gaps.js) next to the candidate shape it comes from.

**Verified** in the real editor ([editor-snap-guides.test.js](../../www/test-e2e/editor-snap-guides.test.js)): a drag where both rhythms apply shows exactly one vertical and one horizontal line, each still spanning the canvas, each reading the proposed position; a drag in range of one axis shows one line, not four; and dropping an element into a hole between two others marks **both** its borders (325 and 425 for a 100px box centred in a 250px hole) with the two 75px arrows either side. The per-side edge choice is pinned in [feezal-sidebar-inspector-logic.test.js](../../www/test/feezal-sidebar-inspector-logic.test.js) — reverting either the edge choice or the centring pair fails its own test.
