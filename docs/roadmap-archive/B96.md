# B96 — Source editor for a big site: PayloadTooLargeError + unformatted one-line HTML ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (07/2026).** Opening the **source editor** for a big site threw a server-side `PayloadTooLargeError: request entity too large`, and the source view showed **the whole site as one line** without line breaks.

**Root cause — one bug, two symptoms.** Entering source mode calls `_formatHtml(html)` ([feezal-app-editor.js](../www/src/feezal-app-editor.js)), which **POSTs the serialized site HTML to `/api/format`** for pretty-printing. That route goes through Express's generic `express.json()` body parser, whose **default limit is 100 kb**. A big dashboard's HTML exceeds it, so the server rejects the request with **413 PayloadTooLargeError**; `_formatHtml` sees `!res.ok` and **falls back to returning the raw input** — which is the near-unformatted, single-line serialization (each top-level node on its own line, so `<feezal-site>` and all its content is one giant line). So the 413 in the log and the one-line source are the *same* failure.

**Fix.** Raise the generic JSON body-parser limit from the 100 kb default to **25 mb** (`configureBodyParsers` in `server/src/app.js`), matching the PWA-icon and site-save parsers already at 25 mb. `/api/format` now accepts the big body, formats it, and the source editor shows properly-indented HTML. Still bounded (self-hosted editor, trusted user). Guard test: a JSON body well over 100 kb POSTed to `/api/format` is accepted (not 413).

**Relates:** `server/src/app.js` `configureBodyParsers` (the raised limit — the site-save route at `api.js` was already 25 mb; the generic parser feeding `/api/format` was the bottleneck), `_formatHtml` / `_enterSourceMode` in `feezal-app-editor.js` (the client caller + its raw-fallback), `/api/format` + `format-html.js` (the pretty-printer).
