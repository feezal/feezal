# U99 — Snap helper lines: position readout on each line ✅ done
*Archived roadmap item — Editor UX. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Requested (08/2026).** The snap guide lines should carry a small label with the line's canvas position — the treatment the [U89](U89.md) gap arrows already give their pixel distance. Vertical lines: `left: 240`, rotated a quarter turn left so it runs parallel to the line, near the bottom of the canvas. Horizontal lines: `top: 320`, unrotated, above the line, near its left end.

## No extra DOM: the line carries its own value

The inspector writes the number to `data-pos` on the line it just positioned, and the CSS renders it with `content: attr(data-pos)`. That means no label element per line to create, move, hide and keep in sync — a line that moves takes its readout with it, and a line that is hidden hides its readout by construction.

Applied to all four N11 edge guides (both vertical, both horizontal), to the [B113](B113.md) full-canvas gap-snap lines, and to the resize path, which snaps to the same edges and had the same lines.

## The value is view-relative, and for y that is a correction

The label has to show the number the element's own `left`/`top` style uses, not where the line happens to sit. Vertical guides already carry view-relative x. Horizontal ones do **not**: their positions are computed in container-relative y (`rect.y - cvTop`), because that is the coordinate the lines are drawn at. So the readout subtracts a new `viewTopInCv`, the vertical twin of the existing `viewLeftInCv`.

This is [B114](B114.md)'s audit applied to the readout, and it is not a scrolled-canvas edge case: the view sits below the tab bar inside the container, so the two spaces differ by a constant even at rest — an uncorrected label was wrong on every drag, not just a scrolled one. (Confirmed by reverting it: the readout test fails unscrolled.)

**Styling** follows the guides rather than the arrows: the label inherits the line's own colour, so it reads as part of the guide instead of competing with the accent-coloured gap proposal. `pointer-events: none`, like everything else in the overlay — the whole thing is painted during an active drag, and a label that could take a hit would break the gesture.

**Verified** in a real editor ([editor-snap-guides.test.js](../../www/test-e2e/editor-snap-guides.test.js)) by reading the *computed* `::after` content, which is where the rendered text actually exists: an edge guide reads `left: 0` / `top: 200` for the element it snapped to, every line paints exactly what it carries, the vertical readout is rotated (`matrix(0, -1, 1, 0, …)`) while the horizontal one is upright, nothing intercepts the pointer, and the gap helper lines carry the same values. The arithmetic — including the scrolled-canvas case — is pinned in [feezal-sidebar-inspector-logic.test.js](../../www/test/feezal-sidebar-inspector-logic.test.js).
