# B86 — Discovery picker stamps nothing on selection; Generate still works (regression, cause verified) ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Fixed (07/2026)** in `www/src/feezal-discovery-stamp.js`, `www/src/feezal-sidebar-inspector-attributes.js` (+ `www/test-browser/discovery-picker-selection.test.js`).

**The separator was the bug.** `DISCOVERY_ROW_SEP` is now `'|'`, lives in the shared headless module and is **interpolated** into the template rather than written in its static text — so the HTML parser never sees it and no future separator can be mangled either. It satisfies three properties, each now asserted: survives an HTML parse, cannot occur in the percent-encoded id half (`encodeURIComponent` escapes it), and is not a space (Shoelace's multi-value delimiter).

**Both halves fixed.** The select's value now carries the linked row's index too (`encodeURIComponent(id) + SEP + index`), so it matches a real option instead of being cleared by Shoelace — a linked device shows as selected again.

**The silent guards are loud.** Both early returns (`!entity`, `!el`) now `console.warn`. A pick that stamps nothing must never again look like a pick that did nothing.

### The test, and two false greens on the way to it

The regression test goes through a **real Lit render** and a **real `sl-select`**, and binds to the **exported production constant** rather than a local copy. Getting there took two mistakes worth recording, because both are the same mistake this bug was made of:

1. The first version asserted the encoding round-trips by setting `option.value` **as a property** — which bypasses the HTML parser entirely, so it passed with the bug fully present. That version was written *during the investigation* and briefly "proved" the encoding was fine.
2. The second version rendered through Lit but declared its own `const SEP = '|'`. Reverting the source to NUL left it green — it was testing a copy of the constant, not the constant.

Only an **HTML-parse round-trip** (`template.innerHTML = ...` then read the attribute back) reproduces the original failure. Verified in both directions: red with the NUL separator restored, green with `'|'`.

**The gap that let this ship:** E156 covered `stampDiscovery()` exhaustively and never exercised *selection*, so a picker that silently stamped nothing passed everything. Unit-testing the mechanism is not testing the path.

---

**Reported (07/2026).** Picking a device in an element's ⚡ discovery picker **stamps no attributes at all**. First seen with an ESPHome sensor, then found to affect **every** discovered device and, apparently, every element. **The Generate wizard is unaffected — it still stamps correctly.**

**Very likely a regression from [E156](roadmap-archive/E156.md)**, which rewrote exactly this path (`_renderDiscoveryPicker` option encoding + `_onPickDiscovery`) to carry a per-axis row index. Generate was untouched and still works, which fits.

## Narrowed by measurement — what is NOT broken

Each of these was verified directly; do not re-investigate them:

1. **Server-side discovery ingest is fine.** ESPHome publishes *abbreviated* keys (`stat_t`, `unit_of_meas`, `dev_cla`, `avty_t`); running the reporter's exact payloads through the real registry expands them correctly. The stored config holds `state_topic`, `unit_of_measurement`, `device_class` and `availability_normalized`.
2. **`stampDiscovery()` and `discoveryCandidates()` are fine.** Fed that exact entity with a `*-value` descriptor, the stamp yields `subscribe`, `unit`, `label`, `subscribe-availability` and `discovery-id` correctly, and the entity produces exactly one candidate row.
3. **The Shoelace value encoding survives.** In real Chromium an `sl-option` whose value is `encodeURIComponent(id) + '\u0000' + index` round-trips **byte-exact** through `sl-select`; splitting on `\u0000` and decoding recovers the id — including ids containing `/` (ESPHome `node_id` form) and spaces (Homematic).
4. **`_applyDiscovery()` reads correctly** — it takes `selectedElems[0]`, calls the shared `stampDiscovery`, then redraws.

**So the fault is isolated to the picker-only path:** `sl-change` → `_onPickDiscovery` → `_applyDiscovery`. Everything on either side of it is proven good.

## ✅ Root cause (verified on the reporter's device, 07/2026)

**The NUL separator never survives.** Live probe output when picking a Homematic thermostat:

```
raw value    : "hm-climate%3A000A9D89B67B42�1"
encId / idx  : "hm-climate%3A000A9D89B67B42�1"   undefined
decoded id   : "hm-climate:000A9D89B67B42�1"
entities     : 710   match: false
selectedElems: 1
```

That character is **U+FFFD REPLACEMENT CHARACTER**, not NUL.

**Why.** The separator sits in the **static** text between two `${...}` expressions inside an attribute binding:

```js
value="${encodeURIComponent(c.entity.discovery_id)}\u0000${allMatches.indexOf(c)}"
```

Lit prepares a template by building an HTML string and letting the **HTML parser** create a `<template>`. Per the HTML spec, a NUL encountered in *attribute value state* is replaced with **U+FFFD**. So the separator is destroyed at template-preparation time, before any value is ever assigned.

**The failure chain, all silent:** `split('\u0000')` finds nothing → returns a single element → `rowIndex` is `undefined` → the decoded id keeps a trailing `�<index>` → `find(e => e.discovery_id === id)` misses → `if (!entity) return;` → **no attributes, no error, no feedback**. `selectedElems: 1` confirms the selection was fine; the id was the only problem.

Note `entities: 710` and the `sample ids` shape (`switch/esphome-test/gpio`) — the cache was healthy. Only the mangled id was at fault.

**Why the Generate wizard is unaffected:** it never round-trips an id through an `sl-option` attribute; it holds entity objects directly.

**Why this escaped testing.** The browser check written while investigating assigned `option.value` **as a property** (`o.value = v`), which bypasses the HTML parser completely — so the NUL survived and the test passed. The bug only exists on the path where the value is authored *in a Lit template*. Testing the mechanism rather than the user's path, a third time in this same investigation.

## Fix

**Change the separator.** It must (a) survive HTML parsing, (b) never occur in `encodeURIComponent` output — which leaves only alphanumerics and `-_.!~*'()` unescaped — and (c) not be a space, since Shoelace treats that as a value delimiter. **`|` or `,` satisfy all three**; `|` reads more clearly.

Then, in the same pass:

- **Align the select's value with the options'** — it currently binds the bare encoded id with no index suffix, so it can never match an option and Shoelace clears it to `""` (measured). Append the linked row's index, or resolve the row at render time.
- **Make the early returns loud.** `if (!entity) return;` and `if (!el) return;` produced a completely silent no-op; a `console.warn` would have made this a five-minute diagnosis instead of a multi-round one.
- **Consider dropping the packed-string encoding entirely** — a `data-row-index` attribute on the option, or an index-keyed lookup, avoids inventing a separator and cannot be mangled by the parser. Encoding two fields into one attribute string is what created the whole failure mode.

## Live diagnostic — paste in the editor console, then pick a device

⚠️ **Select an element on the canvas first** — the attributes inspector does not exist until something is selected. And it lives inside the editor's **shadow DOM**, so a plain `document.querySelector` returns `null`; the walker below is required.

```js
(() => {
  const deep = (sel, root = document) => {
    const hit = root.querySelector(sel);
    if (hit) return hit;
    for (const n of root.querySelectorAll('*')) {
      if (n.shadowRoot) { const r = deep(sel, n.shadowRoot); if (r) return r; }
    }
    return null;
  };
  const el = deep('feezal-sidebar-inspector-attributes');
  if (!el) { console.warn('inspector not found — select an element on the canvas first'); return; }
  if (el.__probed) { console.log('probe already installed'); return; }
  el.__probed = true;
  const orig = el._onPickDiscovery.bind(el);
  el._onPickDiscovery = v => {
    const [e0, i0] = String(v).split('\u0000');
    const id = e0 ? decodeURIComponent(e0) : null;
    const ents = el.__discoveryEntities || [];
    console.log('raw value    :', JSON.stringify(v));
    console.log('encId / idx  :', JSON.stringify(e0), JSON.stringify(i0));
    console.log('decoded id   :', JSON.stringify(id));
    console.log('entities     :', ents.length, 'match:', !!ents.find(x => x.discovery_id === id));
    console.log('sample ids   :', JSON.stringify(ents.slice(0, 3).map(x => x.discovery_id)));
    console.log('selectedElems:', el.selectedElems?.length);
    return orig(v);
  };
  console.log('probe installed on', el.localName);
})();
```

Reading it:

| observation | conclusion |
|---|---|
| `raw value` empty, or no `\u0000` in it | the option encoding or Shoelace delivery is at fault |
| `match: false` — compare `decoded id` against `sample ids` | the `discovery_id` mismatch between the render list and the selection list |
| `entities: 0` | the cache is empty at selection time |
| `selectedElems: 0` | the selection is lost by the time the handler runs (plausible — opening the picker moves focus) |
| all look right, still nothing stamps | the fault is past `_onPickDiscovery`; instrument `_applyDiscovery` the same way |

## Second, independent defect found while measuring

The select's value and its options' values **can never match**:

```js
value="${encodeURIComponent(linkedId)}"                                   // select: bare id
value="${encodeURIComponent(c.entity.discovery_id)}\u0000${index}"         // option: id + NUL + index
```

Measured: Shoelace clears the select's value to `""` when it matches no option, so an already-linked device **never shows as selected** in the closed picker. Fix by using the same encoding on both sides (or resolving the linked row's index at render time). Real regardless of the stamping bug, and probably arrived with the same change.
