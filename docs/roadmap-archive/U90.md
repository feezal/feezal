# U90 — Grid layout for views: `child-position: grid` ✅ done
*Archived roadmap item — Editor UX. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

## Problem

A `child-position: flow` view (U41) lays its children out with **flexbox**, and
flex lines are independent: an item can never span two of them, and a line's
height is set by its tallest item. So a view holding one deliberately
double-size tile — the reported case was a `basic-camera` at exactly 2× the
width and height of the surrounding cards — leaves the space beside the tile's
lower half permanently dead. No combination of `flex-*` properties fixes this;
it is structural.

## Why not a hand-rolled packing algorithm

The obvious reading is that feezal needs its own layout engine ("smart flow").
It does not: **CSS grid does exactly this natively**, and delegating to the
browser keeps the editor, the viewer and the static export rendering
identically for free — the same reason U41 put flow's flex rules in
`feezal-view` rather than in editor code.

Measured on the reported geometry (one 520×380 tile, eleven 245×180 tiles,
5 columns):

| | rows | content height |
|---|---|---|
| `flow` (flex) | nothing beside the big tile's lower half | 1120 px |
| `grid` | three cards backfill beside it | 920 px |

## Design decisions

**A third `child-position` value**, not a change to `flow`. Existing flow views
must keep laying out exactly as before; `absolute | flow | grid` mirrors how
U41 added `flow` alongside `absolute`.

**Spans are derived, not configured.** Each tile's span comes from the size it
already carries: `span = round((size + gap) / (cell + gap))`. Rounding (not
`ceil`) so a tile a few px off a clean multiple lands on the nearest cell count
instead of always growing.

**The cell size defaults to the smallest child.** This is what makes switching a
view to grid look right with zero configuration: the ordinary tiles define the
cell and the deliberately-big one spans 2×2. `grid-cell-width` /
`grid-cell-height` override it.

**Tiles are quantised to their span area** (`width/height: auto !important` on
slotted children). The authored inline size is never touched — it is the span's
source of truth, and switching back to flow/absolute restores it — but it
cannot also drive rendering, or a 520 px tile would overflow its rounded 495 px
area and overlap its neighbour. The editor's drag lift is exempt via
`.feezal-lift`, since a lifted tile is fixed-positioned under the pointer at its
real pixel size.

**Dense packing is opt-in** (`grid-dense`, default off). `grid-auto-flow: dense`
lets a later tile move *backwards* into an earlier hole, which packs tighter but
decouples visual order from DOM order — and DOM order is precisely what
reorder-by-drag (U33/U41) edits, so with dense on you would drop a tile into a
visual hole and it would land somewhere else. Measured: DOM `a b BIG c d`
renders sparse as `a b / BIG c / d` and dense as `a b c / BIG d`. Notably the
reported case needs no dense at all — the big tile is first, so the following
tiles flow forward into the gap without any backwards placement.

**Spans are applied as `::slotted(:nth-child(n))` rules in a generated shadow
stylesheet**, never as inline styles on the children. The editor serializes
inline styles into `views.html`, so per-child layout artifacts there would both
pollute saved markup and fight the B80 absolute↔flow geometry hand-off.

## Implementation

- `feezal-view.js` — the `grid` CSS block, the `grid-*` knobs, cell resolution,
  span-rule generation into a constructable stylesheet (with a `<style>`
  fallback), and an rAF-coalesced `MutationObserver` on child `style` /
  `childList` so editor resizes and reorders re-lay out live.
- `isFlowLike(view)` is exported from `feezal-view.js` and now backs **every**
  editor gate that means "the container places its own children" —
  align/distribute, the Style inspector's top/left suppression, palette
  drop-by-DOM-order, and canvas init. Previously each of these hard-coded
  `=== 'flow'`, which is exactly why adding a mode used to mean hunting them
  down one at a time.
- Grid reuses `initFlow` unchanged for drag-reorder: the placeholder is sized
  from the dragged tile's rendered rect (its cell area in grid mode), so it
  claims the same span in flight, and `_flowMovePlaceholder`'s row-major hit
  test stays valid as long as dense is off.
- `feezal-lift` added to the editor's save-time class stripper, so a drag
  interrupted mid-flight cannot persist it.

## Verification

Unit (`test/feezal-view.test.js`, 8 new): cell derivation and override,
rounding, nth-child indices accounting for the drag placeholder, gap
arithmetic, dense flag, sheet/observer teardown on mode exit, knob visibility.
Browser (`test-browser/feezal-view-grid.test.js`, 8 new): the real layout —
flow leaving the space dead vs grid filling it, grid shorter than flow for the
same content, quantisation, derived cell, sparse-vs-dense divergence, live
re-layout on resize with a clean light DOM, and full teardown on leaving grid.
Live-driven in a real editor and viewer: identical row geometry in both, drag
lift keeping its pixel size, and a lossless grid → absolute → grid round-trip.
