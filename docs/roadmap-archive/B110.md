# B110 — e2e suite intermittently red on a passing run (temp-dir teardown race) ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Observed (08/2026), twice in one session.** The e2e suite reported `Tests 191 passed (191)` and `Test Files 1 failed` at the same time:

```
FAIL  test-e2e/undo-redo.test.js
Error: ENOTEMPTY: directory not empty, rmdir '/tmp/feezal-e2e-…/sites/undoredo/.git/objects'
```

Every assertion passed; the failure was in `afterAll`.

**Root cause.** `stopStack()` did:

```js
stack.serverProc?.kill('SIGKILL');
await rm(stack.dataDir, {recursive: true, force: true});
```

`kill()` only *requests* the exit — it does not wait for it. So the removal walked the tree while the server (or a `git` child it spawned for version history) was still writing into `sites/<name>/.git/objects`. `rm`'s recursive delete empties a directory and then `rmdir`s it; a file created in between makes that `rmdir` fail with `ENOTEMPTY`. `force: true` does not cover this — it only ignores paths that are already *missing*.

**Fix.** Wait for the process to actually exit before touching its data directory, then retry the removal a few times with a short backoff for children that outlive it.

Cleanup failure now warns instead of throwing. That is deliberate: the directory lives under the OS temp dir, and the code runs *after* every assertion — failing a green suite over it teaches you to distrust the signal, which is the real damage. A CI that goes red on a passing run devalues every other result it reports.

**Verified:** the previously flaky file run three times in a row, exit 0 with zero `ENOTEMPTY`, plus a full 35-file e2e run clean.
