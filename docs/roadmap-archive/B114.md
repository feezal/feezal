# B114 — Snapping misplaced by the scroll offset on an undersized, scrolled browser ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (08/2026).** With the browser window undersized and the canvas scrolled to the right, snapping landed in the wrong place — offset by what looked like exactly the scroll width, and probably the same vertically.

## It was the PAGE scroll, not the canvas scroll

The item pointed at the B8 `viewLeftInCv` correction and the `#container-view` scroll delta. That was the wrong suspect, and measuring said so immediately: the canvas scrolls inside `feezal-site`, and `getBoundingClientRect` already accounts for that, which is why B8 only ever needed a correction for where the guide *lines* are drawn.

What actually scrolls on an undersized window is the **page**. Measured in a real editor at a 1000px viewport, `document.documentElement.scrollWidth` was 1465 against a client width of 1000 — the editor shell overflows horizontally and the window gets a scrollbar of its own.

And that is the mismatch:

- **interact.js works in PAGE coordinates** (client + window scroll). It hands the snap-target function page coordinates and reads the returned target back as page coordinates.
- **Every measurement in the snap path is CLIENT space**, because it comes from `getBoundingClientRect`.

Identical while the page does not scroll — which is the normal case, and why this survived so long. Scrolled, every distance is inflated by the scroll amount, so with a 300px page scroll a snap that should engage at 6px was computed as 306px away and never fired at all. The same handoff bug sat in the drag **restriction**: `_dragRestriction()` returns client coordinates and interact reads the rect as page coordinates, so an element dragged to the left edge landed **exactly 300px past it** — the reported "offset by the scroll width", measured.

## Fix

Converted at the interact boundary, not inside the shared implementations: `_snapForInteract()` shifts the query into client space and the answer back into page space, and `_restrictionForInteract()` offsets the rect. Both axes, one documented seam.

Deliberately **not** a change of coordinate space inside `_snap()` / `_dragRestriction()`, because both have other callers that are already in client space and would then have needed the inverse correction: `_snapSize()` derives client coordinates itself (interact hands size snapping plain width/height, which carries no origin) and feeds them straight in, and the palette's new-element drag calls `_snap()` with coordinates it built from `getBoundingClientRect`.

## Verified

[editor-snap-guides.test.js](../../www/test-e2e/editor-snap-guides.test.js) drives a real interact drag at a deliberately undersized viewport (set BEFORE the editor loads — resizing afterwards is not the same thing) and asserts the page really scrolled before each trial. Reverting the shims fails both the scrolled-snap and the restriction case.

No vertical twin at that level: dragging toward the top of the window makes the browser re-scroll the page mid-gesture, so `window.scrollY` cannot be held at a known value long enough to prove anything (measured — it decayed from 150 to 83 during one drag). The vertical term is pinned instead in [feezal-sidebar-inspector-logic.test.js](../../www/test/feezal-sidebar-inspector-logic.test.js), which exercises both shims directly on both axes, including the identity case when the page is not scrolled.

**One test-only trap worth remembering:** parking an element past the right edge of the *visible* canvas makes `feezal-site` grow a scrollbar, and the drag that brings it back removes that scrollbar mid-drag. interact captured the element's start rect before the layout shift, so the element lands ~12px off its snap — a test artifact that looks exactly like a product bug and cost a diagnosis round.
