# U107 — layout-app two-level follow-ups: drag-handle entries editor, two-row tab bar, chevron-only collapse ✅ done
*Archived roadmap item — Editor UX. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (08/2026)** after first use of the shipped [U103](U103.md) two-level navigation. Three follow-ups, each opt-in or knob-controlled.

## 3. Chevron-only collapse — the default FLIPPED, deliberately

New knob `section-toggle: chevron | header`, default **`chevron`** (the reporter's preference; the item explicitly allowed flipping since the feature was days old — documented here and in the knob's help). In chevron mode a section header click **always navigates** to the section's landing page (opening it if needed) and never collapses; the chevron is its own control — a pure toggle, no navigation, with its own hit area and hover feedback. `header` restores the U103 behaviour exactly, and in that mode the chevron is inert on its own (bubbles to the header). The keyboard tree pattern (Left/Right on a focused header) is untouched in both modes — the U103 test that pinned the old default now pins it *under the knob*.

## 2. Two-row tab bar — an option on `tabs`, as the item leant

`tab-sections: drawer | row` (default `drawer`, unchanged), NOT a fourth `nav-style` — so the drawer/no-drawer choice stays orthogonal. With `row`, the sections render as a **first tab row** (childless top-level entries included, in tree order) and the active section's pages as the second row beneath; a childless active entry shows no pages row. Both rows get the U103 overflow treatment independently (`_syncTabOverflow` loops all rows now), and `_onTabKeydown` was scoped to `e.currentTarget` — with two rows, arrows stay within one row and Tab crosses, which also required giving the pre-existing keyboard test a real `currentTarget`.

## 1. Drag handles — a pure move model under the pointer wiring

Every entries-manager row gets a **⠿ handle**; rows are drop targets with three zones on top-level rows (edges = before/after, middle band = *into*) and two on sub-rows. The semantics live in an exported pure function, `moveEntry(list, from, target, mode) → list | null`, so they are directly testable without simulating native DnD:

- **before/after** insert into the target's sibling list — reorder at either level, and the way a sub-entry moves *out* to the top level;
- **into** on a section appends; **into** on a childless item **converts it to a section with exactly the `_indent` semantics** (its own view becomes its first child, the icon stays on the section head);
- **sections only move at the top level** — one nesting level is the U103 data model, and an invalid drop returns `null` rather than being clamped: a drop that would change meaning silently is worse than one that does nothing.

The ↑/↓/⇥/⇤ buttons **stay** — the item's accessibility clause lists "the existing buttons" as an acceptable keyboard path, and keeping them is the least-risk way to not regress it. The clunk is gone because a pointer never needs them.

**Verified** in `test-browser/feezal-elements-layout-app.test.js` (71 green): chevron vs header mode incl. the inert-chevron case and keyboard in both; the two-row tabs (render, section switch, childless direct-navigate, scoped arrows); and the whole move model (reorders, re-homes, the childless conversion, the one-level guard, no-op self-drops). Reverting each feature fails its own cases — including the subtle ones (dropping the one-level guard, weakening the conversion to a plain append).
