# U80 — Generate wizard: the App generator always creates a new site (name → deploy → viewer link) ✅ done
*Archived roadmap item — Editor UX. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Follow-up fixes (07/2026).** (1) The auto-deploy silently didn't run because the resume hook used `feezal.app.updateComplete?.then?.()` — if `updateComplete` was ever undefined the whole resume no-op'd, so `_autoFlow` was never set. Changed to `Promise.resolve(feezal.app.updateComplete).then(…)` so it always fires. (2) A new site ships with an empty scaffold view (`view1`); the new-site flow now **removes any empty pre-existing view** during generation, so Menu is the sole first/default view (the reorder already put Menu first; view1 no longer lingers as the deployed default). (3) **Discovery lag on a fresh site.** The server bridge only connects the new site's inherited MQTT connection as the site loads (`getSite` → `bridge.connect`), and retained-config discovery arrives in a burst a moment later — so `resumeNewSiteApp()` reached the App setup before any device was known and reported "0 devices discovered". Fixed by making `_loadInto` **poll** in auto-flow: `_fetchDevices(stage)` was extracted from `_loadInto`, which now retries up to **12×** at 2s intervals (~24s) while the discovery list is empty, breaking early on the first non-empty result / stage change. While polling, the App setup shows *"Connecting to your broker and discovering your devices…"*; if it stays empty it offers a **Retry** link (`_chooseApp()`). The non-auto (Devices tile / manual App) path is unchanged — `maxAttempts` is 1 there.

**Requested & done (07/2026).** The **App** generator now always builds onto a **new site**, so the user's current site is never touched:

1. **Name first.** Clicking the App tile opens a **new-site name** step, prefilled with the next free **`siteN`** (`site1`, `site2`, … — computed from `/api/sites`). *Create & continue* `POST`s the site with `fromSite: <current>` (inheriting the MQTT broker connection — A-earlier work) and **switches the editor to it** (`window.location.href = /editor/?/<name>/`); a duplicate (409) or a `/`-containing name errors in place without navigating.
2. **Resume on the new site.** After the reload, `loadViews` (feezal-sidebar-inspector) sees the `sessionStorage['feezal:generateAppSite']` flag matches the just-loaded site, clears it, and calls the generate dialog's `resumeNewSiteApp()` — which opens the wizard straight at the **App setup** (axis + family) in an auto-deploy mode. The new site inherited the connection, but discovery lags the site load — the App setup **polls** for it (see follow-up fix 3) rather than reporting 0 devices.
3. **Auto-deploy.** When the wizard's `_generateApp` finishes on the new site, the auto-flow calls `feezal.app._deploy()` so the app is published immediately.
4. **Viewer link.** The result screen shows a **prominent "Open <site> in the viewer"** button (`/viewer/<site>/`, new tab) + an Export hint.

The chosen approach was **Switch to the new site** (user decision) — it reuses the existing site-switch + deploy machinery rather than building off-screen, so it's the lower-risk path; the one reload is early (right after naming) and everything after — wizard, generate, deploy, the viewer-link dialog — runs on the new site. The **Devices** tile is unchanged (adds to the current view). The `window.location.href` navigation is behind a `_navigateTo` seam for tests.

**Ships with:** the new-site name step + `_nextSiteName` / `_confirmNewSite` / `resumeNewSiteApp` / `_navigateTo` in `feezal-generate-dialog.js`, the auto-deploy hook, the prominent viewer link on the result screen, the `loadViews` resume hook in `feezal-sidebar-inspector.js`, the discovery **poll** (`_fetchDevices` + the retry loop in `_loadInto`, the "Connecting…" note + Retry link), browser tests (siteN default, the name prompt, POST-with-fromSite + resume flag + navigation, duplicate error, resume opens at App setup in auto-deploy mode, auto-deploy + viewer link, the App setup polls until devices appear), and a `docs/TESTING.md` line.
