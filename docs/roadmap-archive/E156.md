# E156 — Cross-component discovery: `*-switch` offers lights, `*-slider` offers light axes + `number` ✅ done
*Archived roadmap item — Element ecosystem. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Done (07/2026)** in `www/src/feezal-discovery-stamp.js`, `www/src/feezal-sidebar-inspector-attributes.js`, the new `@feezal/feezal-element/feezal-discovery-fragments.js`, and the 8 switch + 3 slider elements.

**Mechanism — `discovery.accepts`.** A descriptor may now list variants, each with its own map, an optional `when(config)` guard and a `label` suffix:

```js
discovery: {component: 'switch', map: {…}, accepts: [switchAcceptsLight]}
```

`acceptedComponents()` unions the base component, the E150 `aliasComponents` and every `accepts` component; `discoveryMapFor()` picks the variant map when one matches; `discoveryCandidates()` expands the entity list into picker ROWS — one per (entity × matching variant), which is what lets one light produce a brightness row and a colour-temp row (U56's one-entity-→-several-rows shape). The picker options carry the row index so the right variant is stamped.

**Two regressions caught while building it, both from over-reaching on the "which map?" rule.** The first cut said *any* component other than the declared one must use a variant map. That broke:
- **component-agnostic maps** — a descriptor with a `map` but no `component` ("apply this to whatever you are given"), which the stamp test fixtures use;
- **resolver-routed components** — E149 lands a HA `scene` on the *button* element, whose single map deliberately covers both `payload_press` and `payload_on`. Withholding the base map there produced a null publish topic.

The rule is now simply *a matching variant wins, otherwise the base map* — no assumptions about how an entity reached the element.

**Switch ← light.** One shared `switchAcceptsLight` fragment rather than 8 copies. **Its map order is load-bearing and commented as such:** the stamp applies keys in insertion order with later writes winning, and `onlyWhen` can only test equality (there is no "unless"), so the generic `payload_on`/`payload_off` go FIRST and the Homematic override LAST, where its `alsoSet` overwrites them with `1`/`0`. That is what stops a dimmer inheriting the `1.005` OLD_LEVEL sentinel, which a switch cannot represent.

**Slider ← axes.** `sliderDiscovery` has **no base `component`** — a slider has no entity type of its own, so everything arrives through `accepts`: light brightness, light colour temp (mireds taken as the wire unit, not converted to kelvin the way a light card does), and `number`. The settable-only guardrail is expressed as the variants' `when` guard: every one requires a **command topic**, so a `sensor` never appears, a relay lamp with no brightness never appears as a slider, and a read-only `number` never appears.

**Scope note:** applied to the 8 `*-switch` elements, matching the item's wording. `*-checkbox` and `material-chip` also consume the `switch` component and would work identically — left alone deliberately rather than widened without being asked.

**Known limitation:** `discovery-id` still stores only the entity id, so when one light is offered as two slider rows the picker's *displayed* selection resolves to the first row. The wiring is correct either way; only which row shows as selected is approximate. Encoding the axis into `discovery-id` would have touched the re-link and Generate paths, which was more than this item needed.

**Ships with** the mechanism, both fragments, the picker union + row expansion, 15 unit tests in `www/test/feezal-discovery-cross-component.test.js` (acceptance, both switch payload dialects, per-axis rows with correct scale/mireds, `number`, and every settable-only exclusion including "a sensor is never offered to a slider"), the `docs/TESTING.md` §9 row, and patch bumps on the 12 touched packages.

---

Discovery today matches an element only to entities whose `discovery.component` **equals** the element's declared component ([feezal-sidebar-inspector-attributes.js](../www/src/feezal-sidebar-inspector-attributes.js) — `allMatches = entities.filter(e => e.component === component)`). That's too strict: a device of one component is often controllable by an element of another.

**Two gaps to close:**
1. **`*-switch` should also offer `light` devices** — a dimmer or colour lamp can be driven as a plain on/off switch. HmIP dimmer: `payload-off = 0` / `payload-on = 1` (LEVEL); zigbee light: state `false`/`true` (or `ON`/`OFF`). Currently switches only list `switch`-component devices.
2. **`*-slider` has no discovery at all** — it should offer the **settable numeric axes** of discovered devices: a light's **brightness** and **colour-temp**, and HA **`number`** entities.

**Enabling mechanism (shared): multi-component acceptance.** An element's `discovery` descriptor gains the ability to **accept more than one component**, each with its own map variant — e.g. `discovery: {accepts: [{component: 'switch', map: …}, {component: 'light', map: …}]}` (or `component` staying a string for the common case, plus an `also` list). The picker unions the matches across accepted components; each entity is wired via the map variant for **its** component.

**Decided (07/2026):**
- **Switch ← light:** the switch's `light` map variant wires the light's on/off command/state onto `subscribe`/`publish` with `payload-on`/`payload-off`. **Per-source payloads** (the same observed-source split E126/E127 already do): Homematic dimmer-light (`on_off_source: brightness`, LEVEL) → `payload-on = 1` / `payload-off = 0`, wired from the brightness command topic; zigbee/HA on/off light → `ON`/`OFF` (or the discovered `payload_on`/`payload_off`). An on/off-only light naturally lands here too.
- **Slider ← light, one entry per axis** (decided): a discovered light appears in the slider picker **once per settable axis** — "*<name>* brightness" and "*<name>* color temp" — each wiring that axis's command/state topics + range (`brightness_scale` → `max`; mireds range → `min`/`max`). Same one-entity-→-multiple-entries shape as **U56** ✅ (multi-attribute sensors); the U56 label-suffix work is the pattern to reuse for the axis suffix.
- **Slider ← `number`** (decided): settable numeric with `command_topic`/`state_topic`, `min`/`max`/`step` → the slider's range.
- **⚠ Guardrail — settable only (decided):** the slider must **never** offer a read-only value. A `sensor` (temperature, humidity, …) has no command topic → **excluded**; only axes/entities with a **write path** (light brightness/CT command topics, `number` command_topic) are offered. The axis-enumeration for lights must skip a light that exposes no brightness/CT (that's a switch match, not a slider one).

**Mechanism notes:** the axis-per-entry expansion for the slider is a small **derived-entity** step in the picker (one light entity → up to two slider candidates), analogous to how HA already emits one entity per attribute; keep it in the picker/mapping layer, not by forging fake discovery records. The switch's multi-component acceptance is the simpler half (union + per-component map).

**Ships with:** the multi-component `discovery.accepts` mechanism + picker union, the switch `light` map variant (per-source payloads), the slider `discovery` descriptor (light-brightness / light-CT axis entries + `number`) with the settable-only filter, U56-style axis labels, mapping/recognizer tests (dimmer→switch payloads 1/0; zigbee light→switch ON/OFF; light→slider two axis candidates with correct scale/mireds; **sensor never offered to a slider**; number→slider), TESTING.md discovery-section rows, version bumps per policy.

**Relates:** **N12** ✅ / **E149** ✅ (the discovery engine + component-coverage work this extends), **U56** ✅ (one-entity-→-multiple-picker-entries + label suffix — the slider axis pattern), **E150** ✅ (profile/alias discovery — sibling "one device, flexible target" theme), **E126** ✅ / **E127** ✅ (per-observed-source payload wiring the switch←dimmer variant reuses), material/glass/metro-switch (the switch consumers), material-slider / paper-slider / carbon-slider (the slider consumers — parity **E114**), the `number`/`light` discovery maps (source of the wired keys).
