# U92 — Source view: identifying attributes first + on the opening-tag line (fold-friendly) ✅ done
*Archived roadmap item — Editor UX. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Requested (08/2026).** Collapsing an element in the Monaco source view shows only its FIRST line — the bare opening tag — so every folded element looked identical. Wanted: the identifying attributes on the tag line, so folds stay readable.

The two halves the analysis identified were both needed, and they were built to depend on each other as little as possible.

## 1. Attribute ORDER — at serialization

Prettier never reorders attributes; it prints them in source order, which for feezal is live-DOM insertion order. So the order is decided when the document is written out: `reorderIdentifyingAttributes()` runs in `_clean()` (`feezal-app-editor.js`), which is the shared path for **both** deploy and the source view — one place, no drift between what you read and what is saved.

Priority is `name` for `feezal-view`, `label` then `subscribe` for everything else. It runs on a detached clone in every caller, so removing and re-adding attributes cannot trigger a live element's reactive setters, and it skips elements already in order rather than churning the markup.

## 2. First attributes ON the tag line — a post-pass

Prettier's HTML printer knows exactly two shapes: everything on one line, or the tag alone with EVERY attribute on its own line. There is no "keep the first N beside the tag", so this is a line-level join over its output, in the shared formatter.

Deliberate properties:

- **Not width-aware.** The identifying line may run past `printWidth` — that is the point, it is what you read when the element is folded.
- **Joins only, never reorders.** It merges at most two attributes, and only ones that already lead the element. Hand-written source with `label` further down is left exactly as its author wrote it; half 1 is what guarantees stamped content leads correctly.
- **Stops at the first non-identifying attribute**, and never swallows the line that closes the opening tag.
- **Idempotent** — a joined tag line no longer matches "tag alone", which is what keeps formatting a fixed point.

Result:

```html
        <feezal-element-basic-camera label="Hof" subscribe="frigate/hof/motion"
            class="feezal-element"
            style="…">
        </feezal-element-basic-camera>
```

**Verified** end to end in a real editor: a site deployed with `label`/`subscribe` written **last** comes back through the source view with them leading the tag line, the view carrying `name`, and no glued closing tag. Unit tests cover both halves — the reorder (moves to front, `name` for views, values intact, no-op when already ordered, whole tree) and the join (label alone, subscribe alone, both, neither, an identifying attribute that is NOT first left untouched, the two-attribute cap, and the fixed point).

**Decided against:** swapping prettier for js-beautify. The post-pass is bounded and testable; changing formatter would have re-opened every formatting decision already settled.
