# B65 — Homematic `:0` correlation (availability + battery) breaks for custom-named channels
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Fixed (07/2026)** in `server/src/mqtt/native-discovery.js` (+ `server/test/native-discovery.test.js`).

**Symptom.** Availability (`UNREACH`) and battery wiring is derived from a device's `:0` maintenance channel, whose topic segment was computed by string-transforming the output channel's segment (`:<index>` → `:0`). In RedMatic name-mode a custom-named channel ("Steckdosen Werkstatt") has no `:<index>` and is unrelated to the `:0` segment ("OC8 Hobbyraum:0") — the two share only the `hm.device` id — so the transform produced a **dead topic** and availability/battery silently broke. Cross-cutting: affected every recognizer (climate/contact/cover/light/switch/sensor) and, by extension, E135's `:0` signals.

**Fix.** Added a shared device→`:0`-segment index keyed by `hm.device` (`hmMaintSeg`), populated from the firehose on any `MAINTENANCE` / `channelIndex:0` message. Availability + battery now resolve at **read time** (`applyHmAvailability`): the index first (works for custom-named channels), else the `:idx→:0` string fallback, else **omit** the wiring entirely rather than subscribe a dead topic. All six recognizers now store `_availResolve` inputs instead of building availability at promote time — deduping six copies of the block into one place. Regression test added (custom-named `:0` resolved via the index).

**Interface research (kept for the record).** Native recognizers are RedMatic-only regardless of this bug: they gate on `hm.channelType`/`channelName`, which only RedMatic publishes. ccu-jack (bare VEAP `{v,ts,s}`, address-based topics) and hm2mqtt (`hm_addr`/`hm_unit`/`hm_enum`, no channelType/name) don't auto-discover — so the `:0` correlation gap is moot there (ccu-jack's address topics would make `:0` trivially derivable if discovery were ever extended; hm2mqtt's `hm_addr` is a `hm.device` equivalent). User prerequisite worth surfacing in onboarding: the RedMatic MQTT payload mode must be **"MQTT-Smarthome Extended"** for the `hm` block to appear at all.

**Relates:** N31 (availability — primary victim), E124 (battery — same derivation), E135 (`:0` maintenance signals — same index), E108 (recognizer framework), [B64](B64.md) (found on the same OC8).
