# B60 — Homematic settling: `*-light` slider still jumps with WORKING + LEVEL_NOTWORKING both wired
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Fixed (07/2026)** in `www/packages/@feezal/feezal-element/feezal-settling.js` (+ `www/test/feezal-settling.test.js`).

**Symptom.** A fully wired `glass-light` over a RedMatic Homematic dimmer (`HM-LC-Dim1L-CV`) — with **both** the `WORKING` topic and the settled-values topic (`LEVEL_NOTWORKING`) auto-discovered — jumped: on setting a brightness the slider snapped back to (near) the old value, then a moment later to the target.

**Root cause (confirmed from the reporter's MQTT capture).** With a settled topic wired, `SettlingController.live()` correctly refuses to move the slider during the ramp — but the **`WORKING=false` edge** called `_settle(this._lastLive)`, applying the last *intermediate* live reading. The capture showed two device facts that made this maximally wrong: RedMatic delivers `WORKING=false` ~1 s **before** `LEVEL_NOTWORKING`, and the sole interim `LEVEL` report is ≈ the *old* value. So the WORKING=false edge applied the old value, then `LEVEL_NOTWORKING` corrected to the target — the two-step jump.

**Fix.** `WORKING` and the settled topic are alternative sources for the same job, not complementary — and `LEVEL_NOTWORKING` is a complete, authoritative signal. So when `settledWired` is true, `SettlingController.working()` is now a **no-op**: the control follows `command()` holds + `settled()` reports only. The WORKING-only path (devices with no settled topic) is unchanged. Regression test added (the reporter's exact `command(0.22) → live(0.775) → working(false) → settled(0.22)` sequence asserts `apply` is called with `0.22` only, never `0.775`).

**Relates:** E127 ✅ (the settling controller), E128 (blinds settling — same machinery), E137 (light controller owns the settling wiring), the RedMatic `LEVEL_NOTWORKING` dual-topic convention.
