# B120 — iOS PWA: a view SHORTER than the screen scrolls, revealing grey/white bars; layout-app bar moves ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (08/2026).** In the installed iOS PWA a view *taller* than the screen behaved correctly, but a view *shorter* than the screen could be scrolled down — revealing a grey and a white bar below the content — and the layout-app top bar scrolled away with it.

Both symptoms are one cause seen from two sides, as the item's analysis said: the **document** was scrollable, so it carried the whole app with it and exposed layers nothing had painted.

## The height chain

There was no `100vh` to find — the chain is `height: 100%` all the way down (`html`/`body` → `feezal-app-viewer` → `#container` → `#container-view` → `feezal-site`). That is the same trap by another spelling: `100%` on the root resolves against the **initial containing block**, which under standalone display with `viewport-fit=cover` can exceed the *visual* viewport. Nothing else in the chain has to be wrong for the document to end up taller than what you can see.

So the viewer shell now declares the visible height and refuses to scroll:

```css
html, body {
    height: 100%;                    /* floor for everything else */
    height: -webkit-fill-available;  /* iOS without dvh */
    height: 100dvh;                  /* current engines */
    overflow: hidden;
    overscroll-behavior: none;
}
```

`overflow: hidden` is what makes it structural rather than a matter of getting the pixels exactly right: even if some future metric leaves the document a few px taller, it cannot scroll. A view **taller** than the screen still scrolls — inside `feezal-site`, which has `overflow: auto` and is where that scrolling always belonged.

**Three copies.** The same shell CSS exists in the server-rendered viewer (`server/src/app.js` — the one an installed PWA actually loads), the Vite dev entry (`www/viewer-src/viewer.html`) and the static-export template (`server/src/build/export.js`). All three got the fix in the same shape; fixing only the one you happen to open would have looked like a fix and shipped nothing. Editor untouched.

## What the test can and cannot claim

The iOS metrics cannot be reproduced in the harness: on desktop Chromium `height: 100%` already equals the visual viewport, so a broken shell and a fixed one measure identically — the first version of this test passed against the *unfixed* code, which is exactly the trap worth recording.

So [viewer-no-document-scroll.test.js](../../www/test-e2e/viewer-no-document-scroll.test.js) reproduces the **condition** those metrics create rather than the metrics: it forces the document taller than the viewport and asserts a scroll **gesture** leaves the page at 0. A gesture specifically — `overflow: hidden` deliberately still permits programmatic `scrollTo()`, so a scripted scroll would move the page even with the fix and prove nothing. What the report describes is the page moving under a finger.

Around it: a short view leaves `scrollHeight <= innerHeight` in both orientations, the app still fills the screen (the grey/white bars were the gap between the app and the document), and a tall view still scrolls inside `feezal-site` with the far end reachable — the regression that "stop the page scrolling" could easily have caused.

**Not verified here:** the real device. The remaining manual check is the installed iOS PWA in both orientations, with and without the home-indicator inset.
