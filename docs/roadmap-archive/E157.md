# E157 — Extend E156 cross-component discovery to the remaining on/off and numeric controls ✅ done
*Archived roadmap item — Element ecosystem. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Done (07/2026)** in `@feezal/feezal-element/feezal-discovery-fragments.js` and the 8 consuming elements.

**Scope decision on the open question:** extended to **all five** on/off controls. The reasoning, recorded as asked: the inconsistency is worse than the noise. The 8 `*-switch` elements already list lamps, so a `*-checkbox` that does not becomes an arbitrary exception a user hits without explanation — whereas a longer picker costs only a scroll, and a user who wanted a "setting" simply does not pick a lamp.

**What actually shipped, and where it diverged from the plan above:**

1. **The five on/off controls** — `material-checkbox`, `carbon-checkbox`, `tui-checkbox`, `material-chip` take `switchAcceptsLight` verbatim as predicted. **`paper-checkbox` did not**: it reads from **`topic`**, not `subscribe` (legacy Polymer naming), so the fragment verbatim would have written an attribute the element never reads — a silent no-op, not a visible failure. `switchAcceptsLight` therefore became `makeSwitchAcceptsLight({subscribe})`, with the constant kept as the default spelling so the 8 switches are untouched. Only that one key varies; the whole order-sensitive Homematic branch stays shared. (`paper-switch` was checked and does use `subscribe` — E156 has no latent bug here.)

   The chip's E79 active-state contract needed no change: it declares `payload-on`/`payload-off` and derives `_selected` from them exactly as a switch does, so a light's `ON`/`OFF` lands correctly.

2. **`panel-knob`** — the plan said to hand it `sliderDiscovery` wholesale and let its `number` map become the variant. That would have been a **regression**: the slider's `number` map has no `unit_of_measurement`, and the knob renders a unit next to its readout. Instead the light axes were split out of `sliderDiscovery` as `lightSettableAxes`, and the knob takes those while keeping its own richer `number` map. The sliders are built from the same array, so knob and slider still cannot drift on the light wiring — which was the point of the consolidation.

3. **`readonlyNumericDiscovery`** — new fragment for `material-tank` + `material-progress`, as planned. Mirrors `settable(key)` with `readable(key)`, accepts `sensor` / `number` / a light's brightness, and no variant map contains a `*_command_topic` key at all — asserted directly, so the guardrail cannot be eroded by a later edit rather than merely being absent today.

**Tests:** 25 in `www/test/feezal-discovery-cross-component-rollout.test.js`. Behaviour via fixtures (the element modules pull in md-*/carbon components that cannot instantiate under happy-dom, same constraint as the E156 suite), plus a static parity guard asserting each of the 8 real elements imports the fragment and reaches it from its descriptor — the fixtures alone would pass even if an element had been forgotten. Hardest-pinned property: a read-only display handed a **settable** `number` comes out with **no `publish` attribute**.

Full suites green: 498 server, 1113 www unit, 1126 browser.

**Follow-up to [E156](roadmap-archive/E156.md) ✅.** That item built the `discovery.accepts` mechanism (multi-component acceptance, per-component map variants, `when(config)` guards, per-axis picker rows) and applied it to the **8 `*-switch`** and **3 `*-slider`** elements — matching its own wording. The mechanism is general; the rollout was deliberately not. This item finishes it.

**1. On/off controls that consume `switch` but were skipped (5).** These already declare `discovery: {component: 'switch'}` and would work identically with the existing shared fragment — the change is one import + one `accepts:` line each, no new mapping logic:

| element | note |
|---|---|
| `material-checkbox` | |
| `carbon-checkbox` | |
| `paper-checkbox` | legacy Polymer, same descriptor shape |
| `tui-checkbox` | |
| `material-chip` | tap-to-toggle chip — verify the chip's active-state contract (E79) survives a light's `ON`/`OFF` |

Reuse `switchAcceptsLight` from `@feezal/feezal-element/feezal-discovery-fragments.js` verbatim, including its **order-sensitive** map (the Homematic `alsoSet` override must stay last — see the fragment's comment).

**Open question — is a checkbox the right target for a lamp at all?** A checkbox reads as "a setting", a switch as "a device". Offering every lamp in a checkbox's ⚡ picker may be noise rather than help. Decide before implementing: either extend all five, or extend only the ones that are genuinely device-shaped (chip/checkbox in a controls row) and record the reasoning.

**2. `panel-knob` — a slider by another name.** It already declares `discovery: {component: 'number'}` with `state_topic`/`command_topic`/`min`/`max`, so it is exactly the shape `sliderDiscovery` serves; it should also offer **light brightness / colour-temp axes**. Simplest form: give it `sliderDiscovery` and let its existing `number` map become the `number` variant, so knob and slider stay in step by construction.

**3. Read-only numeric displays — the mirror-image gap.** `material-tank` and `material-progress` have **no `discovery` descriptor at all** and only a `subscribe` (no publish). They are the exact inverse of the slider's settable-only guardrail: they should accept a **`sensor`**, and the *read* side of a `number` or a light's brightness — never a command topic. Worth its own small `readonlyNumericDiscovery` fragment rather than bending `sliderDiscovery`, so the guardrail stays legible in both directions.

**Guardrail (inherited, non-negotiable):** whatever is added keeps E156's rule — a control with a write path is never offered a read-only entity, and a display is never offered something purely because it happens to expose a command topic. The existing "a sensor is never offered to a slider" test is the pattern to extend.

**Ships with:** the `accepts` additions per element, the `panel-knob` consolidation, the new read-only fragment + its consumers, tests mirroring `www/test/feezal-discovery-cross-component.test.js` (per element: accepted components, the wired attributes, and the exclusions), `docs/TESTING.md` §9 additions, version bumps per policy.
