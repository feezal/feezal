# B72 — `device-health`: one list entry per *entity* instead of per *device* (ESPHome / zigbee2mqtt)
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Fixed (07/2026).** The device-health inspector checklist showed **one entry per topic/entity** — an ESPHome (or z2m) device appeared many times.

**Root cause.** `buildHealthDevices` merged a device's entities **by friendly name**. That collapses Homematic (entities share the channel name) but not ESPHome/z2m: each entity has a **distinct name** ("Boiler Temperature", "Boiler Uptime", …) and — for ESPHome — every entity carries the **same** `availability_normalized` (`<node>/status`), so each became its own health candidate.

**Fix.** Key the merge on **device identity**: `config.device.identifiers[0]` → `node_id` → friendly name (the last still collapses same-named Homematic channels). Take the label from `config.device.name` when present, and **union** the signals (battery / availability / fault / sabotage) across the device's entities. One row per physical device now.

**Ships with:** the `buildHealthDevices` rekey + unit tests in `test-browser/feezal-device-health.test.js` (many ESPHome/z2m entities sharing `device.identifiers` collapse to one entry with the device name + unioned signals; distinct devices with the same name stay separate; the Homematic name-merge still works). Patch-bumped `feezal-element-basic-device-health` (→ 0.2.1).

**Relates:** the device-health overhaul (introduced `buildHealthDevices`; this fixes its dedup), `decorateBatteryLow` / `getDeviceGroups` in `server/src/mqtt/discovery.js` (the same `device.identifiers[0]` keying), E124/N31 (the per-entity battery/availability records that duplicated here).
