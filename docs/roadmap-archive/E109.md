# E109 — evcc integration: native discovery + energy/charging elements
*Archived roadmap item — Element ecosystem. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ v1 done (07/2026).** [evcc](https://evcc.io/) (self-hosted EV-charging / energy manager) publishes a rich, flat, retained MQTT tree but **no** Home Assistant discovery, so feezal saw nothing of it. v1 makes it one-click and native-looking: a server-side native recognizer + the loadpoint control cards + an EV node on the generic energy-flow diagram.

**Topic contract** was pinned from docs.evcc.io + `evcc-io/evcc` `core/keys/{site,loadpoint}.go` (no local evcc to test against; a friend's retained dump confirmed site/forecast shapes). Facts: flat scalars (`message-property: payload`), everything retained, LWT `<root>/status` online/offline, writes on a `/set` suffix, root prefix user-configurable. **⚠ battery power is +=discharge** at site level (inverted vs. our flow element); a **heating loadpoint** carries `chargerFeature/heating: true` and reuses `vehicleSoc`/`limitSoc` as °C. All topic assembly lives in one `evccTopics()` helper so a wrong assumption is a one-line fix.

**Native recognizer** ([server/src/mqtt/native-discovery.js](../../server/src/mqtt/native-discovery.js), recognizer 9) — detects the root by **structure** (`…/site/grid/power` + `…/site/battery/soc`), never a literal prefix. Synthesizes:
- one **`energy-flow` site entity** — wires solar/grid/home/battery power + SoC, `invert_battery: true` (evcc battery sign), and the EV node to loadpoint 1's charge power; availability from `<root>/status` → N31.
- one **`evcc-loadpoint` entity per loadpoint** — the full control contract (read + `/set` command topics) plus a `heating` flag (stamped only when true).
Vehicles deferred (live SoC lives on the loadpoint). Discovery-component→element resolution added in `feezal-discovery-stamp.js` (`energy-flow` → material family; `evcc-loadpoint` → the loadpoint cards).

**Elements:**
1. **Energy-flow EV node** — extended the existing generic `material-energy-flow` with a **Car node** (`subscribe-charge`, House→Car flow), an **`invert-battery`** toggle, and a `charge-label`; the battery/car nodes now auto-show when their topic is wired. Deliberately generic (any PV/battery/EV home); evcc discovery just wires it.
2. **evcc loadpoint cards** — a new `@feezal/feezal-controller-evcc-loadpoint` (E137) + **glass / metro / circle** views. Charge mode buttons (Off / Solar / Min+Solar / Fast → `…/mode/set`), charge power, vehicle SoC bar toward the limit marker, session energy, connected/charging status. A **heating loadpoint** shows a **reduced °C view** (current temp from `vehicleSoc`, target from `limitSoc`, power, mode — no car controls), so a mixed wallbox + heat-pump install renders correctly.

**MVP control scope shipped:** loadpoint `mode`, `limitSoc`, `minCurrent`/`maxCurrent`, `phasesConfigured` (the controller publishes all; the cards surface mode + SoC-limit prominently). **Deferred (as decided):** plans/departure, `repeatingPlans`, smart-cost/feed-in limits, the 60 s `batteryMode` auto-reset, and the **forecast/price chart** (#3 — really a dynamic-tariff element, only present with a tariff provider). **Follow-ups noted:** multi-loadpoint charge-power summing for the flow's EV node (currently loadpoint 1), a discovery helper to pre-place these from the Generate wizard, and eink/material loadpoint views (E114 parity).

**Ships with:** the recognizer + `evccTopics()` helper + component resolution; the energy-flow EV node/invert; the loadpoint controller + 3 cards; `www/package.json` + manifest registration; E137 parity coverage for the 3 cards; tests — `server/test/native-discovery-evcc.test.js` (recognizer, structure detection, heating flag), `test/feezal-controller-evcc-loadpoint.test.js` (reads/commands/heating), `test-browser/feezal-loadpoint-cards.test.js` (render + mode command + °C view); a TESTING.md §6 row.

**Relates:** E108 (the native-recognizer framework this reuses), material-energy-flow (the generic diagram extended here), E63 (animated-flow technique), N31 (availability from evcc's LWT), E137/E114 (controller + parity), A18 (kiosk/wall-panel placement), the pure-MQTT principle (native recognition, no second transport).
