# E128 — Homematic blinds: settling behaviour + `DIRECTION` indicator ✅ done
*Archived roadmap item — Element ecosystem. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Done (07/2026)** in `@feezal/feezal-controller-cover` (+ the four cover views, the Homematic recognizer, `@feezal/feezal-element/feezal-movement.js`).

Landed **inside `CoverController`** per the sequencing note — E137 had already extracted it, so every cover family (circle / glass / metro / eink) got both halves at once.

**Settling.** E127's `SettlingController` applied unchanged, with the same three wiring tiers and the same attribute names (`subscribe-working` / `message-property-working` / `subscribe-settled` / `message-property-settled` / `settle-timeout` / `report-delay-ms`). Cover-specific choices:
- `settle-timeout` defaults to **60 s** (the light's is 5) — blind travel is 30–60 s, so the dimmer default would reconcile mid-travel.
- **STOP cancels the hold.** A halted blind's target is void, so `stop()` calls a new `SettlingController.cancel()` (added with this item) — abandon the hold WITHOUT applying a value, so the next report lands immediately. `settled()` would have applied a stale mid-travel reading instead.
- **Up/Down arm the settler too** when their payload is a numeric target inside the device range — which is exactly the Homematic case (the recognizer wires both buttons to the LEVEL set topic with payload 1 / 0). A non-numeric OPEN/CLOSE (z2m) predicts nothing and is left alone.
- **Separate mode only.** The json (z2m/HA) path infers position from several fields at once; routing it through a numeric settler would change z2m behaviour for no gain, and the WORKING/LEVEL_NOTWORKING tiers are the Homematic dialect this exists for.

**Tilt: yes, the helper applies.** Venetian slat angles ramp exactly like the position, so the tilt slider gets its own `SettlingController` instance fed by the SAME channel `WORKING` signal (one datapoint covers both movements). `LEVEL_NOTWORKING` carries the position only, so the tilt settler is deliberately created with `settledWired: false` and keeps following its live topic. *Flagged for a real-hardware pass on a venetian actuator* — the mechanism is symmetric and safe either way (a device that doesn't ramp echoes the target immediately and settles at once).

**`DIRECTION` indicator.** Optional `subscribe-direction` (+ `message-property-direction`, `payload-direction-up`, `payload-direction-down`), read by the shared `parseDirection()` — the Homematic enum verified against OpenCCU-Base `rf_keymatic.xml` (`NONE` / `UP` / `DOWN` / `UNDEFINED`, device values 0…3), accepting both the option NAME and the numeric index because interfaces differ. The controller exposes `direction` / `moving`; the views render the shared `movementBadge()` (a pulsing ▲/▼, top-left) — except **eink**, which draws a STATIC ▲/▼ glyph instead (the family forbids animation) and includes the direction in its `renderSignature()` so the redraw dedup can't swallow it.

**Recognizer.** The Homematic cover recognizer now OBSERVES `WORKING`, `LEVEL_NOTWORKING` and `DIRECTION` alongside `LEVEL` — never promoted on their own, and the config keys are emitted only for datapoints actually seen on the broker (the E127 no-guessing rule).

**Shipped with:** the controller fragment (patch bumps + E114 parity, which derives automatically from `COVER_CONSUMED_ATTRIBUTES`), the four views' indicator + reflected properties, the recognizer update, `docs/TESTING.md` §2, and tests in `www/test-browser/feezal-movement.test.js` + `server/test/native-discovery.test.js`.

---

Blinds/covers have **the same LEVEL ramp problem** as dimmers (position reports trail the command while the blind travels) — deliberately split from **E127** so the settling machinery ships and hardens on lights first.

- **Settling:** apply E127's shared helper to the `*-cover` family's position slider unchanged — same attributes (`subscribe-working`, `message-property-working`, `subscribe-settled`, `settle-timeout`, `report-delay-ms`), same three wiring tiers, same discovery observation (`LEVEL_NOTWORKING` / `WORKING` siblings of the blind channel). Blind travel is much slower than a dimmer ramp — the cover default for `settle-timeout` needs to be generous (blinds can travel ~30–60 s; default around 60 s, still configurable).
- **`DIRECTION` datapoint (the blind extra):** blind actuators additionally expose **`DIRECTION`** (mqtt-smarthome `{val}`; enum: none / up / down) while moving. Wire it as optional `subscribe-direction` + `message-property-direction` and render a **movement-direction indicator** on the cover card (e.g. animated ▲/▼ arrow while travelling, per family style) — also observed-only in discovery. Kept in this item, **not** in E127.
- Tilt/slat settling: check whether the slat angle reports ramp the same way on venetian actuators; if so the helper applies to the tilt slider too — verify on real hardware during implementation.

**Ships with:** cover-family attributes + help texts (patch bumps, E114 parity), recognizer update, TESTING.md notes (slow-travel timeout, direction indicator, tilt check).

**Sequencing vs. E137 (controller extraction):** either order works — if E128 lands before `CoverController`, it wires E127's `SettlingController` directly (as planned above) and migrates into the controller with the rest of the cover behavior; if the extraction lands first, E128's settling + `DIRECTION` wiring is implemented *inside* `CoverController` (and every cover family gets it at once). The settling attributes end up in the controller's declared fragment either way (E137's settling decision).

**Relates:** **E127** (the machinery this reuses — do first), **E137** (controller extraction — cover settling ends up inside `CoverController`; see sequencing note), E108 ✅ (recognizer), E114 (parity), E120 ✅-era cover-discovery work (same recognizer area).
