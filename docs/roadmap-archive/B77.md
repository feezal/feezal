# B77 — Background editor: gradient-stop percent input still too small (B73 fix insufficient) ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Fixed (07/2026)** in `www/src/feezal-style-editor-background.js` (+ `www/test/feezal-style-editor-background.test.js`).

Both fix directions were taken, because either alone would have left it tight:

- **92 px** (from 68). The diagnosis was right that the B73 widen was eaten by chrome, not digits.
- **`no-spin-buttons`** on both inputs (Shoelace supports it natively, so no `type="text"` switch and no hand-rolled clamping — `min`/`max` stay native). A typed 0-100 / 0-360 value has no use for up/down arrows, and dropping them returns the width the screenshot showed the arrows wasting.

**Plus the reason the angle input looked even worse than the stop inputs:** the rule was `.stop-row .pct`, and the gradient **angle** input carries `.pct` but lives in `.row` — so it never matched, and the angle field **never got B73's widen at all**. It was rendering at the browser's default number-input width the whole time. The selector is no longer scoped to `.stop-row`, so both uses get the same treatment.

**Covered by tests** (the item asked for it if the markup changed): the `.pct` rule is asserted to be unscoped and ≥ 92 px, and a mounted gradient editor is asserted to render three `.pct` inputs that all carry `type="number"` + `no-spin-buttons` with the `°`/`%` suffixes intact — so a future re-scoping or a dropped attribute fails the suite instead of shipping.

**Not changed:** the Style-inspector percent inputs the item suggested checking use their own layout and do not share this class or the too-narrow pattern.

---

**B73 ✅ is not actually fixed** — the gradient-stop (and angle) percent inputs are still too narrow to read; the screenshot shows the value (`0` / `10`) crammed against the `%` suffix with the number-spinner arrows overlapping it.

**Why the B73 bump didn't take:** B73 widened `.pct` from 52 px → **68 px** ([feezal-style-editor-background.js:165](../www/src/feezal-style-editor-background.js#L165)), but each input is an `sl-input type="number"` with a `<span slot="suffix">%</span>` ([feezal-style-editor-background.js:638-640](../www/src/feezal-style-editor-background.js#L638-L640)). At 68 px the **native number-spinner arrows + the `%` suffix + internal padding** consume nearly the whole field, leaving almost no room for two/three digits — so the widen was swallowed by chrome, not the digits.

**Fix directions (pick during implementation):**
- **Widen further** — 68 px is empirically too small; go to ~92–100 px so digits + spinner + `%` all fit. Simplest.
- **And/or drop the spinner** — a 0–100 value users type doesn't need up/down arrows; hiding the number-spinner (`::-webkit-inner-spin-button`/`appearance:none`, or `type="text"` + numeric `inputmode`) reclaims the width the screenshot shows the arrows wasting. Keep `min`/`max` clamping in the change handler.
- Applies to **both** `.pct` uses — the gradient-stop position (0–100 %) and the gradient **angle** input ([:611](../www/src/feezal-style-editor-background.js#L611)) which shares the class (angle is 0–360, wants even a touch more room).

**Acceptance:** a three-digit value (`100`, `360`) is fully visible in the stop/angle inputs with the `%`/suffix legible and no arrow overlap, in both editor light and dark mode. Extend `test/feezal-style-editor-background.test.js` if the markup changes (e.g. spinner removal).
