# E154 — `*-lock`: indicate lock movement (motor moving / direction / settling) ✅ done
*Archived roadmap item — Element ecosystem. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Done (07/2026)** in `@feezal/feezal-controller-lock` (+ circle / glass / metro lock, the Keymatic recognizer, `@feezal/feezal-element/feezal-movement.js`).

**The settling question, answered.** The build flagged it as expected: `SettlingController` is numeric (hold a slider at a target until the reports catch up) and does not fit a discrete lock state. So the movement package gained a small **`MovementController`** — the discrete-state analog, sharing the file (and the `parseDirection()` reading) with E128 rather than generalizing the numeric settler into something that serves neither well.

**State model.**
- `command(intent, expected)` — Lock / Unlock / Open enter the transitional state immediately; the device confirms only when it is done, and some interfaces echo the OLD state first, so an echo of the pre-command state cannot cut the hold short.
- `signal(active, hint)` — the movement datapoint. **While wired it is the authority**: it extends the state (so a physical key turn or another app's command shows too, with the direction naming the intent) and idle ends it — not the STATE report.
- `report(state)` — ends the hold only when no movement datapoint is wired, and only on the expected state.
- `movement-timeout` (default 20 s) always resolves, so a lost `DIRECTION=NONE` can never strand a card on "locking…". A **jam** drops the state at once — the motor failed.

**Datapoints verified** against OpenCCU-Base `rf_keymatic.xml` per the repo's Homematic-source rule: `DIRECTION` is an enum `NONE`(0) / `UP`(1) / `DOWN`(2) / `UNDEFINED`(3), and Keymatic indeed has **no** `WORKING` — `DIRECTION` is the movement signal. Which way the motor turns to lock is mounting-specific, so it is not hardcoded: `payload-direction-lock` / `payload-direction-unlock` (defaults `DOWN` / `UP`, numeric indices also accepted) make a swap a one-attribute fix, documented in the help text. A device publishing a plain boolean "motor running" flag instead reads as a neutral **moving…**.

**Views.** `movementText` replaces the resolved state text while transitional, and the family's own lock visual takes the shared `.feezal-moving` pulse class — no extra chrome, and it respects `prefers-reduced-motion`. (The Lottie lock-turn animation stays the E139 `fancy-lock` showcase.)

**Discovery.** The Keymatic recognizer OBSERVES `DIRECTION` and emits `direction_topic` / `message_property_direction` only when the datapoint was actually seen — the E127/E128 observed-only rule. **HmIP-DLD is still not wired** (its `LOCK_STATE` / motor datapoints need real-device confirmation — that stays with E144); when it lands, the movement attributes are already there to point at it.

**Shipped with:** the controller fragment + state model (patch bumps; E114 parity derives from `LOCK_CONSUMED_ATTRIBUTES`), the three views' rendering + reflected properties, the recognizer update, `docs/TESTING.md` §2, and tests in `www/test-browser/feezal-movement.test.js` + `server/test/native-discovery.test.js`.

---

Lock cards currently snap between **locked ⇄ unlocked** with nothing shown while the motor is actually turning. Homematic Keymatic (and HmIP door locks) take a second or two to lock/unlock/open, and expose a **movement signal** — the lock analog of the blind `DIRECTION`/`WORKING` machinery (**E128**) and the maintenance-signal work (**E135**, whose Keymatic `ERROR` is already wired into `feezal-controller-lock`). The card should show a transitional **"locking… / unlocking… / opening…"** state, ideally direction-aware, instead of a silent flip.

**Homematic datapoints (verify at implementation against [OpenCCU-Base `rf_keymatic.xml`](https://github.com/homematicip/OpenCCU-Base) / HmIP legacy map, per the repo's Homematic-source rule):**
- **BidCoS Keymatic (HM-Sec-Key):** `DIRECTION` enum — expected `NONE` / `UP` / `DOWN` / `UNDEFINED`; non-`NONE` = the motor is turning, and the value distinguishes locking vs unlocking. This is the movement signal (Keymatic has **no** separate `WORKING` datapoint — `DIRECTION` plays that role). `STATE`/`ERROR`/`LOWBAT` already handled.
- **HmIP door lock (HmIP-DLD):** verify the motor/lock-state datapoints (`LOCK_STATE`, and a motor/`PROCESSING`-style field) — the E144 "HmIP-DLD open" work is the natural place to confirm the exact names.
- **zigbee2mqtt / others:** most expose only lock/unlock state (no movement) — the indication is additive and simply absent when unwired, exactly like E128's cover direction.

**Design (mirrors E127/E128, adapted to a discrete state):**
- **Movement/direction attributes on `feezal-controller-lock`** (behavior lives in the controller — all four family views inherit it): `subscribe-direction` + `message-property-direction` and a value→{idle, locking, unlocking, opening} mapping (Keymatic `DIRECTION` UP/DOWN → locking/unlocking; the OPEN action → opening). Optional `subscribe-working`-style boolean for devices that expose one instead.
- **Settling** (the E127 idea, but the state is discrete not numeric): on a user lock/unlock/open command, **hold a transitional "…ing" state** until `STATE` confirms the new value **or** `DIRECTION` returns to `NONE`, with a `settle-timeout` fallback — so the card doesn't flicker to a stale STATE mid-move. The numeric `SettlingController` doesn't fit directly (discrete states); a small **state-settling analog** in the controller, or a generalization of the settling concept, is the implementation choice — flag at build.
- **Visual** (per family, parity **E114**): a moving/animated lock while transitional — pulsing or a rotating shackle, direction-aware (turn one way locking, the other unlocking); this is a **standout for `fancy-lock` (E139)** where a real Lottie lock-turn animation fits. glass/metro/circle show a subtler spinner/label. Idle when no movement signal is wired.
- **Discovery:** the Keymatic recognizer wires `subscribe-direction` from the observed `DIRECTION` datapoint — **observed-only**, exactly like E127 wires `WORKING`/`LEVEL_NOTWORKING` (no blind guessing).

**Ships with:** controller attributes + state model, the four family views' movement rendering, recognizer wiring for Keymatic `DIRECTION` (+ HmIP-DLD once E144 confirms it), parity-test coverage, tests (command → transitional hold → STATE/DIRECTION settle → resolved; timeout reconcile), TESTING.md §6 rows.

**Relates:** **E128** (the cover `DIRECTION` + settling design this mirrors for locks), **E127** ✅ (settling concept — discrete-state analog here), **E135** ✅ (Keymatic `ERROR` already in the lock controller — the sibling maintenance signal), **E137** ✅ (`feezal-controller-lock` — where this behavior belongs), **E144** (Keymatic/HmIP-DLD lock discovery — supplies `DIRECTION`; HmIP-DLD datapoint confirmation), **E139** (fancy-lock — the animated-movement showcase), **E114** (family parity), the Homematic-source rule in the repo instructions (datapoint verification).
