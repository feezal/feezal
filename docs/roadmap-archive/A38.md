# A38 — Drop DragSelect: hand-rolled rubber-band selection ✅ done
*Archived roadmap item — Architecture & Infrastructure. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Analyzed (08/2026), on request.** The question was whether interact.js could take over the rubber band — it cannot (interact.js ships draggable/resizable/dropzone/gestures, no selection module, and never has), but the analysis showed DragSelect is not necessary either: a replacement would not lean on interact.js at all, it is plain pointer-event work.

**What feezal actually used** (`_initDragSelect`): the selection rectangle overlay, the selectables registry (`addSelectables`/`removeSelection`), rect-vs-element hit-testing during the drag, and the end-of-gesture callback. Deliberately NOT used: its keyboard drag (disabled), its click selection (feezal's own composedPath handler covers clicks — U41 flow views have no DragSelect and select fine), and even `selectedClass` was overridden — the callback re-synced `feezal-selected` by hand.

**Why replaced — the workaround surface outweighed the feature:** three archived lifecycle bugs (B2, B35, B48) were pure DragSelect fights; `.dragselect-rectangle` DOM junk had to be scrubbed before serialization in three places; the `_dsDidDrag`/`_ignoreNextClick` dance kept its events from clobbering feezal's own selection handling; and it was the README's only GPL-3.0 call-out.

## How it shipped

`www/src/feezal-canvas-rubberband.js` — a zero-dependency `RubberBand` class (~230 lines with the comments): pointer-down on empty canvas → a fixed-position overlay → `getBoundingClientRect()` intersection against `.feezal-editable` → apply `feezal-selected` → `_updateSelection()`.

**The three lifecycle bugs dissolve structurally rather than being re-worked-around**, which was the point of the exercise:
- **B2** (a view still `display:none` when the canvas was wired produced a zero-size selector area that swallowed every click): nothing is measured at wire-up time. Rects are read when the gesture happens, by which point the view is laid out by definition.
- **B35** (`stop()` was not idempotent and wiped the selectables set): there is no selectables registry. Elements are queried live at gesture end, so nothing needs re-seeding and stopping twice is a no-op. The per-view instance map is gone too — one instance is retargeted, so `_viewChanged` no longer stops a set of competing instances one by one.
- **B48** (an instance stayed bound to a detached view node): `bind()` always retargets at the live node.

**Serialization**: the overlay is created on gesture start and removed on gesture end, so it never exists when markup is serialized. The three scrub sites are kept only as a self-heal for sites saved before this change, and are commented as such.

## The load-bearing side effect nobody had declared

Removing the library broke seven e2e tests across three files that had nothing to do with selection: element drags clamping to the wrong extent, the canvas no longer being scrollable with an element below the fold, and align/distribute writing wrong offsets. One mechanism explained all of them.

**`feezal-view` never declared `position`.** Every element's inline `top`/`left` is view-relative — that is what the style inspector writes, what B80 stashes and restores across a mode switch, and what align/distribute computes against — but that only holds while the view is a *containing block*. DragSelect set `position: relative` on its area element, so the editor had been getting one for free; the viewer got away with it because a 100 %-sized view lines up with its parent anyway, making the bug invisible rather than absent.

So the rule now lives in `feezal-view` itself:

```css
:host([child-position="absolute"]) { position: relative; }
```

…where the viewer and the static export see it too, which is where it should have been all along. It is pinned by a browser test that asserts a child of an *offset* ancestor still measures 50/100 from the view — verified to fail when the rule is removed. Container-placed (flow/grid) views deliberately stay `static`, and that is asserted as well.

This is the most valuable thing the migration surfaced: a dependency was silently supplying a layout invariant the codebase depended on and never stated.

**Auto-scroll** was re-implemented (a scroll step per rAF while the pointer is within 24px of the scroll container's edge) rather than dropped. **Touch** is covered by using Pointer Events, which handle mouse/touch/pen through one path.

**Behaviour kept**: modifier-drag (shift/ctrl/meta) adds to the selection; locked elements stay band-selectable; a press that starts on an element belongs to interact.js; a right-press opens the context menu; a press below a 4px threshold is left to the click handler, which owns "empty canvas → select the view".

**Licensing**: `dragselect` removed from `www/package.json` and the lockfile, and the README credits line dropped. It was the only GPL-3.0 dependency, so `GPL-3.0` / `GPL-3.0-only` / `GPL-3.0-or-later` were removed from the license gate's allowlist — verified by re-running the gate (400 production dependencies, all allowlisted). The comment there now records that GPL would still be *compatible* with feezal's AGPL-3.0 core, but that a future GPL dependency should be a conscious, argued exception rather than a silent inheritance.

## Verification

`test-browser/feezal-editor-rubberband.test.js` (15) replaces the DragSelect lifecycle suite, keeping B2/B35/B48 as explicit named regressions — "the new implementation cannot have this bug by construction" is a claim that deserves a test — plus the selection behaviours DragSelect used to provide. `test/feezal-canvas-rubberband.test.js` (7) pins the hit-test geometry, including that merely touching edges is not a hit. Two real bugs were caught by these tests before any manual run: `_onPointerUp` tore the gesture down before computing hits (so every band selected nothing), and the overlay's border inflated its measured size.

Live-driven in a real editor: band selects, overlay draws mid-drag, the inspector's `selectedElems` agrees with the CSS class, click-select and shift-band-add work, empty-canvas click selects the view, element drag still belongs to interact.js, banding works after a view switch and on revisit, and `_clean()`ed markup contains no band artifacts.

**Relates:** **A37** (the canvas-interaction-engine extraction this shrinks — done first deliberately, so A37 extracts the already-simplified code), B2/B35/B48 ✅ (the regression fence), U41 (flow views already selected without DragSelect — proof the click path was independent), A34 (dependency policy — one dep fewer).
