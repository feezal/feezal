# B67 — Battery / availability badge parity gaps (circle-climate battery; metro availability)
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Fixed (07/2026).** A device advertised a badge attribute (auto-stamped by discovery / spread by an E137 controller) yet never rendered the badge — the low-battery / offline state was computed and silently dropped. Fixed across the affected elements and locked with a render-level parity test.

**Reported (same device as [B66](B66.md)).** `circle-climate` showed **no battery badge** for a device reporting low battery — the warning was invisible. A follow-up audit found this was one instance of a broader **badge-parity** hole spanning both the battery *and* availability badges.

**Cause.** The badge was *declared but never rendered*. `circle-climate` declared the full E124 battery quartet, so autodiscovery stamped the topic and `ClimateController` tracked `climate.batteryLow` — but the element didn't import `batteryLowBadge` / `feezalBatteryStyles` and had no `batteryLowBadge(...)` call in `render()`. Same shape on the availability side: several `metro-*` device elements accepted `subscribe-availability` but drew no unavailable badge.

**Fixes.**
- **`circle-climate` battery badge** — imports `batteryLowBadge` + `feezalBatteryStyles` and renders `${batteryLowBadge(this.climate.batteryLow)}` top-left, mirroring the top-right unavailable badge (minding B66 so it doesn't overlap the label).
- **`metro-climate` / `metro-switch` / `metro-light` availability** — gained the `subscribe-availability` attribute set + a `renderBadge()` that shows a `!` while unavailable (metro-climate already had battery; it lacked availability). (`metro-fan` does not exist — the metro device elements with the gap were these three.)
- **`glass-climate` badge placement** — the sibling fix, archived separately as [B66](B66.md).
- **`*-value` availability (opt-in)** — `circle-value`, `glass-value`, `metro-value` now show an availability badge when `subscribe-availability` is wired and the device goes offline (per family convention: circle SVG, glass `⚠`, metro `!`). Opt-in — the badge only appears once an availability topic is configured; the last value stays shown.

**Audit results.**
- *Battery:* cross-referencing "declares `subscribe-battery-low`" vs. "calls `batteryLowBadge(...)`", `circle-climate` was the **only** element that declared it but didn't render it. Every other battery-capable element (circle-contact/motion/sensor, plus climate/sensor/motion/contact/lock across glass / metro / eink) already rendered it.
- *Availability:* the metro family was missing it on `metro-climate` / `-switch` / `-light`; the circle / glass / eink device elements already rendered it, and `*-value` had none until this fix.

**Guard against regressions — the parity test.** This was an **E114 parity** hole made easy by the E137 controller attribute-spread: an element advertises `subscribe-battery-low` / `subscribe-availability` (auto-stamped by discovery) yet forgets to render the badge. `www/test-browser/feezal-controller-parity.test.js` now drives **real MQTT messages** through the shared bus and asserts the badge actually appears in the shadow DOM:
- every element that accepts `subscribe-battery-low` renders `.feezal-batt-badge` after a low-battery message;
- every device element that accepts `subscribe-availability` renders an unavailable badge after an offline message — recognising all family conventions (`.unavail`, eink `.badge-tr`, metro `.badge` `!`, and the shared `.feezal-unavail-badge` helper).

The test derives its element sets from each class's declared `feezal.attributes`, so a newly-added element that declares a badge attribute is automatically pulled into the assertion — the "declared-but-not-rendered" class of bug can't be reintroduced silently. (It caught two elements — `circle-wled`, `glass-fan` — that render via the shared `availabilityBadge()` helper, which is why the selector set includes `.feezal-unavail-badge`.)

**Ships with:** the `circle-climate` battery-badge render; the availability badge on `metro-climate`/`-switch`/`-light`; the opt-in `*-value` availability badge (circle/glass/metro); the render-level parity test; patch bumps on every touched element package.

**Relates:** [B66](B66.md) (the sibling glass badge-placement bug), E124 (the battery-low badge/record), N31 (the availability/unavailable badge), E114 (parity — declared/accepted-but-not-rendered is a parity gap a test should catch), E137 (controllers spread the battery/availability attributes, which is why the mismatch is easy to introduce), glass-climate / the metro sibling elements (reference implementations), `feezal-element` (`batteryLowBadge` / `feezalBatteryStyles` / `availabilityBadge`).
