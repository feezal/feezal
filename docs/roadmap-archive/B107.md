# B107 — Source formatting: closing tag glued to the last attribute line ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (08/2026).** Multi-line elements closed like this:

```html
            style="width: 200px; height: 40px; top: 0px; left: 6px"
            visible=""></feezal-element-basic-navigation>
```

**Same family as B105**, and B105's `htmlWhitespaceSensitivity: "ignore"` alone does **not** fix it — verified rather than assumed. `bracketSameLine: true` parks the `>` on the last attribute line, and for an EMPTY element the closer glues straight onto it. So this needed the targeted post-pass B105 had held in reserve.

**Fix:** a line-level pass over prettier's output in the shared formatter, so deploy and the source view stay identical. A line ending `></tag>` whose content starts with a non-`<` character is a *continuation* line, and is split into the attribute line plus a closing tag one indent level out:

```html
            visible="">
        </feezal-element-basic-navigation>
```

Two things keep it safe:

- **Compact elements are untouched.** `<tag a="1"></tag>` starts with `<`, so it never matches — splitting those would be churn, not formatting.
- **No indent tracking needed.** Prettier's indentation is regular: attribute lines sit one `tabWidth` deeper than their opening tag, so the closer's indent is the attribute indent minus one level.

Idempotent by construction (a split line no longer matches), which the fixed-point test pins.

**Verified** in `server/test/format-html.test.js`: no glued closer, the closing tag alone on its line, indented level with its opening tag, compact elements left alone, and the double-format fixed point.

**Relates:** **B105** ✅ (same printer, same file — the two passes live in one post-processing step), **U92** ✅ (the join pass alongside this split).
