# U97 — Slim editor footer/status line ✅ done
*Archived roadmap item — Editor UX. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Requested (08/2026).** A slim always-visible status line at the bottom of the editor — the classic IDE footer — with a sensible fixed set of segments for v1.

## What v1 shows

Selection echo (the element's type and label, or the view when nothing is selected, or a count for a multi-selection), then views, elements, an estimated serialized size, the number of distinct subscribed MQTT topics, and the active theme.

## The footer owns no model

Every segment is derived from the site DOM at render time; the component holds nothing but two revision counters. That is what keeps it from drifting out of step with the canvas — there is no cached count to forget to invalidate.

The single subscription is a `MutationObserver` on the site, and the reasoning is the one the Layers panel already settled: elements are added by the palette, the clipboard, the generate wizard, the AI assistant and the source editor, while selection is written as a *class* by the canvas. Asking each of those to notify a footer is five chances to miss one; observing the DOM covers them all, including the two lifecycle cases that version had to learn — a site that arrives **late** (the shell renders its chrome before the socket delivers the markup, so a one-shot attach leaves the footer permanently empty) and a site that is **replaced** when the editor switches sites.

Two details worth keeping:

- **The size estimate is cached against a structural revision.** `outerHTML` walks the whole site, and a drag rewrites classes every frame; paying for that per frame is exactly what the split between `_revision` (anything) and `_structure` (childList only) avoids.
- **Elements are counted as direct children of views**, which is the canvas's own model: a component instance is ONE element, and the children it stamps inside itself are not separately selectable or movable. (Also: `feezal-element-*` is not a CSS selector — there is no wildcard tag match — so the count uses the same `isCanvasElement` predicate as the rest of the canvas. The first version did use it as one, and quietly counted views as elements.)

## Layout row, not overlay

The shell shortens `#container` by exactly the footer's height, named once as `--feezal-footer-height`. An overlay would cover the bottom edge of the canvas, which is where elements get dragged to.

`feezal-footer` went into the editor's `:host(.dark)` propagation list **in the same commit that created it**, which is the whole of B102's lesson: the component reads `--feezal-*` with light fallbacks, so being absent from that list renders it white in a dark editor. The ratchet in `test/editor-dark-palette-propagation.test.js` would have caught it, but not needing to be caught is the point.

**Deferred:** the zoom segment. U97 named the footer as the home for [U84](../ROADMAP.md)'s zoom indicator instead of a floating tray, and that still holds — but U84 itself is not shipped (see its roadmap entry for what the attempt measured), so a control for a zoom that does not exist would be worse than none.

**Verified** in `test/u97-footer.test.js`: the counts follow the canvas as elements are added, the selection echo tracks the class the canvas writes, a late site is picked up by the retry, a swapped site is re-observed, an attribute-only change does not re-measure the size, and a detached footer stops observing.
