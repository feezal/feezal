# B104 — Multi-selection drag: elements snap to their co-dragged companions ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (08/2026).** Dragging a multi-selection made the elements snap to THEMSELVES: the co-dragged elements acted as snap targets for each other, so the group jittered and magneted against its own members while moving.

**Root cause:** the element-snapping scan in `_snap()` excluded only `this.dragElement` and `this.resizeElement` — the single-drag case. In a multi-selection drag the OTHER selected elements ride along via the group-move logic but stayed in the target set.

**Fix:** one predicate, `isMoving(element)`, defined once in `_snap()` and used by **both** sibling scans:

```js
const isMoving = element => element === this.resizeElement
    || element === this.dragElement
    || (Boolean(this.dragElement) && Boolean(this.selectedElems?.includes(element)));
```

Two details worth keeping:

- **Scoped to an active drag.** Outside one, a selection parked elsewhere is stationary and remains a perfectly good snap target — excluding it unconditionally would have quietly cost real snapping. Asserted by its own test.
- **Defined once, used twice.** The exclusion was duplicated across the drag scan and the general scan, which is exactly the shape that lets one of them drift. The optional chain on `selectedElems` matters too: `_snap` is reachable with the array unset, and a bare `.includes` threw — caught immediately by two pre-existing B8 snap-line tests, which were left untouched and the code fixed instead.

**Verified** in `test-browser/feezal-editor-drag-restrict.test.js`: a co-dragged companion sharing an edge is ignored, a stationary unselected element still snaps, a parked selection still snaps when no drag is active, and the resized element is never its own target. Confirmed to fail when the exclusion is reverted.
