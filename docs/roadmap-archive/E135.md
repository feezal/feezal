# E135 — Homematic maintenance signals: fault + sabotage badges, device-health board
*Archived roadmap item — Element ecosystem. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Done (07/2026).** Homematic's two under-used, actionable maintenance signals — **fault reporting** (stuck valve, clutch/motor fault) and **sabotage** (case-opened/tamper) — now surface both as **per-element badges** and on a **device-health board**, alongside the E124 battery and N31 availability signals.

## Shared decoder + badge infra — `@feezal/feezal-element/feezal-hm-fault.js`
- **Family-keyed classic enum tables** (the same number means different things per family): `HM-CC-RT-DN` `FAULT_REPORTING` (0 NO_FAULT … 4 COMMUNICATION_ERROR … 7 VALVE_ERROR_POSITION), `HM-Sec-Key` `ERROR` (clutch/motor), `HM-Sec-SC` `ERROR` (7 = SABOTAGE). `decodeHmFault(deviceType, value)`.
- **HmIP named-flag → text** map (`ERROR_JAMMED` → "Jammed", …) and `hmipFlagText`.
- **Two sabotage encodings**: classic `ERROR == 7` (`error7`) vs. HmIP `SABOTAGE` bool (`bool`) — `isSabotageActive`, `isHmSabotageValue`.
- The shared attribute fragment `faultSabotageAttributes` (`subscribe-error`/`-sabotage` + property twins + `error-device-type` + `sabotage-encoding`), the `subscribeFaultSabotage(host, {onError,onSabotage})` wiring helper, and the alarm-grade `sabotageBadge` / warning-tier `faultBadge` templates + `feezalFaultStyles`. All unit-tested.

## Device-health board — `feezal-element-basic-device-health`
The "is everything okay?" wall panel. Runs **discovery-less** on wildcard subscriptions (`<prefix>/status/+/{FAULT_REPORTING,ERROR,SABOTAGE,SABOTAGE_STICKY,LOWBAT,LOW_BAT,UNREACH, HmIP ERROR_* flags}`), device name from the topic segment, severity-sorted (sabotage alarm > fault warning > battery > unreach), clears on OK. Browser-tested.

## Per-element badges (auto-discovered)
- **Recognizers emit presence-checked canonical records** (`recognizers/homematic.js`): the **contact + sensor** recognizers emit `sabotage_normalized` (classic `ERROR == 7` → `error7`; HmIP `:0 SABOTAGE` → `bool`); the **climate** recognizer emits `error_normalized` for the BidCoS TRV `FAULT_REPORTING`. `stampDiscovery` auto-stamps `error_normalized`/`sabotage_normalized` onto elements declaring the attributes, exactly like the E124 battery record.
- **Controllers decode + expose**: `ContactController`/`SensorController` gained `.sabotage`+`.error`; `ClimateController` gained `.error`. Badges render on **contact / motion / (alarm) sensor** (12 views) and **climate** (4 views) across circle/glass/metro/eink — sabotage alarm-grade (error colour) vs. fault warning-tier, state keeps updating. `circle-lock` already renders the Keymatic `ERROR` fault (E144).

## Research verified against OpenCCU-Base (the CCU's own device descriptions)
- **`FAULT_REPORTING` (HM-CC-RT-DN)** lives on **channel index 4, type `CLIMATECONTROL_RT_TRANSCEIVER`** — the control channel the climate recognizer already tracks (`rf_cc_rt_dn.xml`), so no separate service-channel wiring was needed. Enum confirmed 0..7 as decoded. This dropped the item's last verify-gate.
- **Classic sabotage** = `ERROR == 7` on the sensing channel (no separate boolean on classic HM); **HmIP sabotage** = a dedicated `SABOTAGE`/`SABOTAGE_STICKY` bool on `:0`. Both encodings supported.
- **Wall thermostat (HM-TC-IT)** has no fault datapoint (no valve) — so not every "climate" device gets a badge (presence-checked, correct).

## Deferred (verify-gated, same rule as E131/E144)
The **HmIP-eTRV named-flag / numeric `MAINTENANCE.ERROR_CODE` valve faults** are not auto-emitted — the config doesn't carry the per-device enum, and guessing a wrong enum mis-reads state. The board still surfaces HmIP `ERROR_*` flags by name, and manual `subscribe-error` wiring works; auto-emission for HmIP eTRVs lands once a real-device `ERROR_CODE` dump confirms the enum. HmIP-DLD lock faults ride E144's deferred slice.
