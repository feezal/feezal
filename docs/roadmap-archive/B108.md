# B108 — Stale viewers linger in the Clients list ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (08/2026).** The Clients panel accumulated viewers that are long gone.

## The last-will IS wired — and still cannot cover everything

Both halves of N24's cleanup exist and work:

- **direct-MQTT viewers** register a broker last-will that clears the retained status (`presenceWill()` → retained empty publish, wired in `feezal-connection-mqtt.js`);
- **bridge-backend viewers** register their status topic with the server, which clears it when the socket drops (`socket.on('presence')` / `disconnect` in `socket/hub.js`).

So the common case is handled. The leaks come from cases an LWT structurally cannot reach:

1. **A site with its own configured LWT gets no presence will at all.** MQTT allows exactly ONE will per connection, and the code gives an explicitly configured `lwt`/`lwp` priority. Such a site's viewers never clear their status on an ungraceful exit — permanently.
2. **A renamed viewer's will still points at its OLD topic.** The will is fixed at connect time; after `rename` the new ID has no cleanup behind it, and the old topic is what gets cleared.
3. **Changing the site's publish topic strands every existing retained status.** Nothing ever publishes to those topics again, so nothing clears them.
4. Even in the happy path the LWT only fires after the broker's keepalive timeout, so there is always a lag.

A retained status with nothing to clear it looks online forever. That is what was in the list.

## Fix: a heartbeat, so absence is observable

**Viewer** (`feezal-presence.js`): re-publish the retained status every 60s while connected (`PRESENCE_HEARTBEAT_MS`). One small retained publish per viewer per minute — far below any broker's traffic concern, and frequent enough to spot a dead viewer quickly. The timer is idempotent across reconnects, stops on teardown, and skips beats while the connection is down.

**Clients panel** (`feezal-sidebar-clients.js`): a viewer with no heartbeat for **3 minutes** (three missed beats, so one dropped publish does not make it vanish) is treated as inactive and hidden, with a summary line — `2 inactive viewers … hidden · Show · Forget them` — so nothing disappears silently. **Show** reveals them greyed out; **Forget** clears their retained status on the broker, which is what actually removes the ghost rather than just hiding it.

**Staleness is measured by LOCAL arrival time, not a timestamp in the payload.** A viewer's clock can be minutes or hours off the editor's, and a skewed clock must never make a live viewer look dead. The panel records when each status *arrived* and re-evaluates on a 15s tick — silence is the event, so nothing else would trigger the re-render.

## Verification

`test/feezal-presence.test.js` (4): the interval republishes retained, stops on teardown, skips beats while disconnected, and never beats when presence is off for the site. `test-browser/feezal-sidebar-clients.test.js` (6): a ghost is hidden while the live client stays, the count is surfaced rather than silently dropped, Show reveals them greyed, a single missed beat is tolerated, Forget publishes the empty retained clear to the right topic, and a cleared client leaves the seen-map.

Adding `connected` to the shared fake connection in the presence tests was part of the fix — the real connection exposes it and the fake did not, so the heartbeat's own guard was untested until it did.
