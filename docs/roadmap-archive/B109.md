# B109 — Layers tree: previous view's selection stays marked after cross-view select ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (08/2026).** Selecting an element on ANOTHER view in the layers tree (U87) correctly switched the view and selected the element on the canvas — but the element selected on the FIRST view still showed as selected in the tree.

**Root cause, as the report predicted.** The tree has no selection state of its own: it mirrors the `feezal-selected` class site-wide. `selectElement()` cleared that class only within the ACTIVE view, so an element on the view you just left kept it. The canvas hides inactive views, which is why nothing looked wrong there — the tree was simply the first surface that reads selection across views.

**Fixed centrally**, per the report's preference: the sweep in `selectElement()` now runs over `feezal.site` rather than the active view. A stale `feezal-selected` is latent state for anything reading selection site-wide, so patching only the tree's path would have left the same trap for the next reader. Falls back to the active view when `feezal.site` is unset (bare prototype receivers in tests, early boot), which is asserted.

**Verified** in `test-browser/feezal-inspector-cross-view-select.test.js`: selecting on another view leaves exactly one marked element, selecting the view itself (empty-canvas click) clears across views, a multi-selection within one view still works, replacing a multi-selection leaves nothing behind on either view, and the no-site fallback does not throw. Confirmed to fail when the sweep is scoped back to the active view.

**Relates:** U87 (the layers tree that exposed it), U33 (selection/stacking model).
