# B89 — HA discovery: nested `device` abbreviations not expanded (ESPHome device metadata lost; switch not offered) ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (07/2026):** an ESPHome switch is not offered by `*-switch` (nor `*-light`) in the ⚡ discovery picker:

```
homeassistant/switch/usb-relay-02/relay/config
{"name":"relay","stat_t":"…/status/relay","cmd_t":"…/set/relay","avty_t":"…/status",
 "uniq_id":"ESPswitchrelay",
 "dev":{"ids":"2cf4321a50ee","name":"Lichterkette Ida","mdl":"esp01_1m","mf":"Espressif","cns":[["mac","…"]]}}
```

**Confirmed root cause — `expandAbbrevs()` was top-level only.** [discovery.js](../../server/src/mqtt/discovery.js) has the mappings (`ids`→`identifiers`, `mdl`→`model`, `mf`→`manufacturer`, `cns`→`connections`, `sa`→`suggested_area`, …) but `expandAbbrevs` only rewrote the **top-level** keys, so the abbreviated keys **inside the nested `dev` object were never expanded**. Verified by feeding the payload through `handleMessage`: the entity IS created (component `switch`, `state_topic`/`command_topic` correct — top-level `stat_t`/`cmd_t`/`avty_t` expand fine) **but `config.device.identifiers` was `undefined`** (it was `config.device.ids`), and `model`/`manufacturer`/`suggested_area` were likewise stuck under abbreviated keys. Any device with abbreviated `dev.*` keys (ESPHome's default) lost its device metadata, and because device grouping keys on `device.identifiers[0]`, the entity dropped/mis-bucketed out of the picker.

**Fix (shipped).** In `server/src/mqtt/discovery.js`:

- `expandAbbrevs` now **recurses into nested objects/arrays**, applying `ABBREVS[k] ?? k` at every level — so `dev.ids`/`mdl`/`mf`/`cns` (and any nested config) expand. Values are never rewritten, only keys. The `components`/`cmps` map is special-cased: its keys are user-chosen object_ids (one of which, `sw`, is *also* an abbreviation for `sw_version`), so those keys are preserved while each component config is still expanded.
- `resolveBase` now recurses too, so the `~` base-topic shorthand resolves inside nested `availability` entries and `cmps` component configs, not just top-level.
- New `normalizeDevice()` converts a **scalar** `device.identifiers` (ESPHome sends a bare string) to a one-element array, so consumers that do `device.identifiers[0]` (device grouping, the Generate wizard, E124 battery-low correlation) don't index into a string.
- The device (`cmps`) discovery path now also runs `normalizeAvailability`, matching the per-component path — device-level availability shared across components is canonicalised too.

**Verified:** the reported ESPHome switch resolves `device.identifiers: ["2cf4321a50ee"]`, `name: "Lichterkette Ida"`, `model: "esp01_1m"`, `manufacturer: "Espressif"`; `getDeviceGroups()` returns one correctly-keyed group so the switch is offered under `*-switch`. Two new regression tests in `server/test/discovery.test.js` assert (a) nested `dev` abbreviation expansion + scalar-identifier normalisation + device grouping for the ESPHome payload, and (b) recursive `~`/abbreviation resolution inside a `cmps` + `availability` array device config. Full server suite (505 tests) green.

**Relates:** **E161** (friendly names / icons / areas — was blocked by this; `dev.name`/`sa` are now readable), **N12** / **E149** (the HA discovery engine), **E108** (native path unaffected — this is HA-only), the `/api/discovery/device-groups` grouping + the Generate wizard (**U58**) that rely on `device.identifiers`, `server/src/mqtt/discovery.js` `expandAbbrevs`/`resolveBase`/`normalizePayload`.
