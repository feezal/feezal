# U100 — Editor min-width instead of broken narrow layouts ✅ done
*Archived roadmap item — Editor UX. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (08/2026).** Below roughly 1484px browser width the editor layout degraded — the sidebar tab items misbehaving in position and behaviour. The editor is not meant to be responsive down to arbitrary widths; the deliberate fix is a floor, so the window scrolls the whole editor horizontally instead of the layout collapsing.

The item's live test had already confirmed 1484px as a solid floor **and** found the blocker: with the min-width set by hand, the right sidebar kept sticking to the *viewport's* right border, and scrolling right revealed empty space past it.

## Two lines, and only one of them is the obvious one

```css
:host {
    display: block; position: relative;
    width: 100%; height: 100%; min-width: 1484px;
}
```

`min-width` is the floor. `position: relative` is what makes the floor mean anything: `#container` — which holds the canvas, the sidebar and the AI panel — is `position: absolute; width: 100%`, and with an **unpositioned host** its containing block was the *initial* containing block, i.e. the viewport. So below the floor the editor host was 1484px wide while its entire body chrome was laid out at the viewport width: the sidebar sat at the viewport's right edge, and the 384px between there and the editor's real right edge was the reported empty space.

Positioning the host makes `width: 100%` resolve against the editor, and every piece of chrome then lays out against the editor's (min-)width and scrolls with it.

The audit the item asked for found nothing else: the remaining `position: fixed` chrome is menus and modal overlays (context menus, the folder menu, the shortcuts overlay), which are *supposed* to be viewport-anchored, and every one of them is positioned from `clientX`/`clientY` — the right coordinate space for fixed positioning, so none of them drift when the page scrolls. Nothing sizes against `100vw`. The editor page's `html`/`body` do not clip overflow, so the horizontal scrollbar simply appears.

**Viewer untouched** — dashboards are responsive by design; this is editor chrome only.

**Verified** in a real editor at a 1100px viewport ([editor-min-width.test.js](../../www/test-e2e/editor-min-width.test.js)): the editor measures exactly 1484px, the page gains a real horizontal scrollbar, `#container` is as wide as the editor rather than the viewport, and the sidebar's right edge is the editor's right edge. Scrolled fully right, the editor's right edge *is* the viewport's — nothing beyond the sidebar — and the sidebar moves with the scroll instead of staying pinned. Above the floor the rule is inert: the editor fills the window and no scrollbar appears.

Reverting each half fails a different set: without `min-width` the floor and scroll cases, without `position: relative` all three sidebar/container cases.

**Relates:** U93 (top-bar rearrangement — reduced the width pressure), the sidebar tab bar (the reported victim), A38 (the same lesson: a containing block that was never declared).
