# B95 — Default playlist attributes serialized onto every `<feezal-site>` ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (07/2026).** In the source editor, **every** site carried the playlist config attributes even when nothing was configured:

```
playlist="" playlist-dwell="10" playlist-resume="60" playlist-transition="none"
```

**Root cause.** The N26 playlist properties on `feezal-site` are `reflect: true` **and** were initialised to their defaults in the constructor (`this.playlist = ''`, `playlistDwell = 10`, `playlistResume = 60`, `playlistTransition = 'none'`). A reflected reactive property writes its value to the DOM — so the defaults materialised as attributes on load and serialized into the saved site HTML (and static exports), noise on a site the user never touched. (`playlist-enabled` stayed absent only because a Boolean `false` reflect removes the attribute.)

**Fix.** Leave the four value-typed playlist properties **unset** in the constructor. A reflected property with no value never writes an attribute, so a default site is clean; the viewer/playlist logic already supplies the same defaults inline (`current?.dwell || this.playlistDwell || 10`, `this.playlistResume || 60`, `String(this.playlist || '')`, and the CSS only matches `[playlist-transition="fade"]`), so an unset property behaves identically. `playlistEnabled` keeps its explicit `false`. Setting any of them (via the Viewer settings sidebar → `_applySite`) still writes + serializes the attribute as before. Guard test: a default site materialises **no** `playlist-*` attribute.

**Relates:** **N26** ✅ (the playlist/signage feature whose config this is), `feezal-site.js` (the reflected properties + constructor), `feezal-sidebar-viewer.js` `_applySite` (the non-default persistence path that still works), the site serializer / static export (which read the DOM attributes).
