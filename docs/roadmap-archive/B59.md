# B59 — Generate wizard: numeric zigbee power sensor becomes a contact element
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Fixed (07/2026)** in `www/src/feezal-discovery-stamp.js` (+ `www/test/feezal-discovery-stamp.test.js`).

**Symptom.** A z2m power meter added via the Generate wizard had its numeric power attributes stamped as **contact** (open/close) cards.

**Cause.** `contact` was the fallback default of the `binary_sensor` branch of `resolveElementTag` (`BINARY_BY_CLASS[deviceClass] || 'contact'`), so any `binary_sensor` with an unmapped or missing `device_class` — including a mis-classified / measurement-ish reading — silently became an open/close card.

**Fix.** The `binary_sensor` fallback now defaults to **`sensor`**, never `contact`: `[BINARY_BY_CLASS[deviceClass] || 'sensor', 'sensor', 'motion', 'contact']`. A genuine opening class (door/window/garage/opening) still maps to `contact`; `contact` also remains the last-resort fallback for a family that ships only a contact card. So a non-opening binary reading is never turned into a contact element. Regression tests added (unmapped/missing class → sensor; door → contact; contact still reachable as last resort).

**Deferred (minor enhancement, not the bug):** defaulting a power/energy device's icon to material `energy_savings_leaf` (a `device_class → icon` default on the value/sensor element) — a nice-to-have, tracked separately if wanted. If the reporter's z2m meter really publishes the power reading as a `binary_sensor` (vs. a numeric `sensor`), the *discovery-layer* classification could also be tightened — but the resolver no longer turns it into a contact regardless.

**Relates:** U58 (Generate wizard), E113 (resolveElementTag = its minimal slice), E114 (parity), E138 (device-function taxonomy).
