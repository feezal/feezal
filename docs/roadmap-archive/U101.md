# U101 — Snap helper-line color configurable + alpha in the editor color pickers ✅ done
*Archived roadmap item — Editor UX. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Requested (08/2026).** A third colour setting beside "Selection color" and "Grid color" for the snap/gap overlay, and transparency in all three pickers.

## What "the guides" turned out to mean

The refinement that came with the request — *element snapping, gap snapping, gap arrows, helper-line labels and gap-arrow labels must all respect the configured colour* — is the whole shape of the fix, because those five surfaces were getting their ink from three different places:

- the **N11 edge guides** borrowed the **grid** colour, written as an inline `borderColor` whenever the grid re-rendered;
- the **[B113](B113.md)/[B116](B116.md) gap lines** had their own hardcoded grey;
- the **[U89](U89.md) gap arrows** used the editor accent, deliberately — B113 reasoned that an active proposal should not look like a passive alignment hint.

They now all read one `--feezal-snap-color`, published by the editor shell. That collapses the accent/grey distinction on purpose: the request was one configured colour for the overlay, and a proposal drawn in a colour the user did not pick is the thing being fixed. The labels needed nothing — both families inherit their line's `color`, which is why the U99 readouts and the arrows' px values followed for free.

The grid coupling had to be **removed**, not redirected: an inline style beats the stylesheet, so leaving it pointed at the new setting would have worked only until someone changed the grid. (It was also nearly invisible: the guides' own positioning writes `cssText`, which wipes inline styles, so the old coupling could only show through between a grid re-render and the next pointer move. The regression test reproduces exactly that window.)

## Alpha

All three pickers are `sl-color-picker` with `opacity` now — the [U66](U66.md) machinery, not a second widget.

The snap colour needed no special handling: nothing composes a second alpha on top, so the authored value is used as-is. **The selection colour is the interesting one.** It reaches its consumers as an `r,g,b` triplet precisely *because* each composes its own alpha — the rubber band fills at 0.12 and borders at 0.8, the selection outline sits at 0.9. Once the setting itself carries alpha the two have to **multiply**, so the alpha travels beside the triplet as `--feezal-selection-alpha` and each consumer scales its own figure by it. An untouched (opaque) setting puts 1 there, which is byte-for-byte the old rendering.

`hexToRgbAlpha()` does the split, and falls back rather than returning `NaN` — the picker emits values mid-keystroke, and a NaN triplet would drop the selection ring off the canvas until the next edit.

**Verified** in a real editor ([editor-snap-guides.test.js](../../www/test-e2e/editor-snap-guides.test.js)) at a drag position chosen to light up **all four** guide families at once — a position missing one would let that family keep a hardcoded colour unnoticed — asserting the painted colour of every line, every label, every arrow and its end ticks. Plus: a colour applied mid-session without a reload, an 8-digit value surviving as `rgba(…, 0.5)`, and the grid re-rendering mid-drag without stealing the guides back. Reverting any one of the four pieces fails its own case.
