# E146 — Autodiscovery for AI-on-the-edge-device (meter reader) via Home Assistant MQTT discovery
*Archived roadmap item — Element ecosystem. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Done (07/2026).** [AI-on-the-edge-device](https://github.com/jomjol/AI-on-the-edge-device) (a hugely popular ESP32-cam that reads analog/digital water/gas/energy meters with on-device AI) is integrated **purely through the device's own Home Assistant MQTT discovery** — no native recognizer.

**The decision (and why native recognition was declined).** Since v12.0.1 the device can publish `homeassistant/<component>/…/config` (opt-in in its web UI), and feezal's existing HA-discovery path already ingests it with the proper `state_topic`, `unit_of_measurement`, `device_class` and `availability_topic` — all resolved *by the device*. A native recognizer would be a swamp that HA discovery makes moot: the base topic (`MainTopic`) is user-configurable and contains slashes (no fixed prefix/depth to match); flat and nested sequence styles coexist; MainTopics nest across devices; stale retained "ghost" sequences linger; `json` values are quoted strings. HA discovery emits one clean `homeassistant/sensor/…/config` per meter regardless of base-topic config.

**What shipped (the item's small scope):**
- **Verified** feezal's HA-discovery path ingests AI-on-the-edge's `homeassistant/sensor/…/config` correctly — pinned by `server/test/discovery-ai-on-the-edge.test.js`: component `sensor`, `state_topic`, `unit_of_measurement`, `device_class` (water/gas/energy), and the `<deviceRoot>/connection` `availability_topic` normalized into the N31 canonical record (topic + payload_available/not_available); multi-sequence devices stay distinct entities.
- **Documented** in the README's auto-discovery bullet: *enable Home Assistant discovery in the device's web UI and the meter appears in feezal automatically.* Plus a TESTING.md verification row (confirm against a real device with HA discovery on).

**Explicitly NOT done:** a native `MainTopic`/`json`-anchored recognizer, base-topic-slash parsing, nested-MainTopic disambiguation, or a meter-topic staleness filter. Reconsider only if a meaningful population runs AI-on-the-edge **without** HA discovery and asks for it. If a real device surfaces an HA-discovery shape feezal mishandles, the fix belongs in the HA-discovery mapping, not a recognizer.

**Relates:** the existing HA-discovery path (the mechanism this leans on), N31 (availability via the device's `connection` topic), E30 (sparkline for the rate sensor), the pure-MQTT principle (HA discovery is pure MQTT), E145 (contrast: ccu-jack has no HA discovery, needs the native route — AI-on-the-edge doesn't), [E147](E147.md) (the dedicated meter element that surfaces the richer json/status/rate topics discovery alone throws away).
