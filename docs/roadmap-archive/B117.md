# B117 — Coinciding gap + edge snap draws the helper line twice ("fat" artifact); drop the label prefixes ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (08/2026).** When a gap snap and an element-edge snap land on the same coordinate — which is common, since a gap-snapped position usually *is* an aligned edge — both passes drew their own helper line there. The doubled dotted line rendered as a **fat** artifact, and the label doubled with it.

## Two lines, and they were not even on the same pixel

The dedupe is the fix the item asked for: the gap pass now receives the coordinates the N11 edge pass has just drawn and skips any line within a pixel of one. The edge guide is the one that stays — they are visually identical, so what matters is a single paint per coordinate, not which pass wins.

The sub-pixel tolerance is not decoration: percentage-sized elements and fractional layout routinely put two "same" coordinates a few hundredths apart, and those paint on one pixel.

Measuring it turned up a second cause of the same fat look, which the report describes but the diagnosis did not name: the two passes did not agree on where a line goes. The N11 guides offset by `-1` horizontally and `-1.5` vertically — a 1px box plus its 1px dotted border paints one pixel right of `left` — while the gap lines used the raw coordinate. So even when the two agreed on the coordinate they drew a pixel apart, which looks exactly as fat as drawing twice. The gap lines now use the same convention, and the dedupe would have been half a fix without it.

## Label prefixes

`left:` / `top:` are gone from the [U99](U99.md) readouts — the value alone (`240`, not `left: 240`). The label's orientation and placement already say which axis it belongs to: the vertical one is rotated and parked at the bottom, the horizontal one is upright above the line.

**Verified** in the real editor ([editor-snap-guides.test.js](../../www/test-e2e/editor-snap-guides.test.js)) with a case that builds the collision deliberately — an element moved so its left edge sits exactly on the gap proposal — asserting exactly one line and one label at that coordinate, with the bare number as its painted text. The test restores the element afterwards, because the *other* cases need the opposite: the fixture's coordinates are chosen so no proposal lands on an edge, or B117 would dedupe the lines those cases are about.

Reverting the dedupe fails that case plus both unit cases (exact and within-a-pixel).
