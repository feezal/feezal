# B115 — Context menus: Delete entries must ALL get the danger red hover ✅ fixed
*Archived roadmap item — Bugs. Open items: [../ROADMAP.md](../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (08/2026).** The element context menu's **Delete** entry hovered like a normal item, with no red danger background — unlike the delete entries in the other context menus. Wanted as a blanket rule: every delete/remove entry in every context menu gets the red hover.

The item had already located it: the machinery sat two lines above the bug in the same stylesheet (`.ctx-item.danger:hover`), applied to "Delete component…" but not to the plain **Delete** row. One word.

## The sweep found a fifth menu, not a fourth

The item listed four menus. There are five: the **assets** panel has its own, and it had drifted furthest — a different class (`.ctx-item.del`), a different red (`#c00`) and a different treatment altogether (red *text*, no red hover). It now matches the rest.

That is the same failure as the missing class, one level up: the rule existed in four-and-a-half copies, so a new menu started from whichever copy its author happened to read. The red is now defined **once**, on the editor host:

```css
:host { --feezal-ctx-danger: #c62828; }
```

Custom properties cross shadow boundaries, so all five menus — inspector, layers, palette, assets, view tabs — read it from there. Two of them were also missing `color: #fff`, which is not cosmetic: dark text on `#c62828` is unreadable, and both now set it.

## The guard is a source ratchet, deliberately

The item asked for "a browser assertion per menu". A source scan is the better shape here: the menus live in five components with quite different mounting requirements, and what needs guarding is not *this menu is red today* but *a row added tomorrow cannot ship un-red* — which is a property of the source, not of one rendered instance.

[ctx-menu-danger.test.js](../../www/test/ctx-menu-danger.test.js) parses every menu row out of `www/src` and fails when a destructive one lacks `.danger`. A row counts as destructive by its **caption or the action it invokes** — a row wired to `_ctxAction('delete')` is destructive whatever it is captioned. It also asserts the red is never hardcoded, that the token has exactly one definition, and that every danger rule flips the text to white.

Two anti-blindness checks come with it, because a scan that finds nothing passes everything: the scan must find the known rows (including the plain **Delete** this item was about), and it must **not** drag in the `.danger` buttons that are not menus (package buttons, site-manager rows, the conditions panel's icon buttons — all legitimately their own thing).

**Verified** by re-introducing each regression in turn: un-marking the element Delete row, returning one menu to a raw hex, and putting the assets menu back on red text. Each fails the matching assertion.

**Relates:** the context-menu family (inspector / layers / palette / assets / view tabs), N43 (the ratchet philosophy — one shared definition beats four copies).
